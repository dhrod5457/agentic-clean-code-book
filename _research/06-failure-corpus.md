# 코딩 에이전트는 어디서 실패하는가

작성일: 2026-10-03  
상태: 리서치 v0.1

이 책에서 어려운 용어를 새로 만드는 것이 목적은 아니다.

오히려 실제 개발자가 코딩 에이전트를 쓰면서 자주 보는 장면에서 출발한다.

- 이미 고쳐진 문제인데 또 코드를 바꾼다.
- 문제는 서비스 로직인데 화면에 조건문을 하나 더 붙인다.
- 한 파일만 고치면 되는 줄 알고 시작했다가 관련 파일을 여러 개 놓친다.
- 테스트는 통과했는데 코드 구조는 더 나빠진다.
- 시키지 않은 설정 파일이나 공통 코드를 같이 정리한다.
- 각자 작업한 두 에이전트의 코드는 따로 보면 맞는데 합치면 깨진다.
- 오류 로그가 너무 길어서 어디부터 봐야 할지 다시 검색해야 한다.

Agentic Clean Code는 이런 실패가 덜 일어나는 코드베이스를 만드는 일이다.

---

## 1. 고칠 필요가 없는데도 손댄다

실제 프로젝트에서는 오래된 이슈가 남아 있을 수 있다.

다른 사람이 이미 고쳤거나, 다른 브랜치에서 수정됐거나, 버전이 올라가면서 자연스럽게 해결됐을 수도 있다.

사람이라면 먼저 재현해보고 "이미 해결됨"이라고 닫을 수 있다. 그런데 코딩 에이전트는 작업을 받으면 뭔가를 바꿔야 한다고 생각하는 경향이 있다.

2026년 FixedBench 연구는 **아무 코드도 바꿀 필요가 없는 200개의 실제 작업**을 가지고 코딩 에이전트를 평가했다. 최신 모델과 에이전트도 35~65%의 경우에 불필요한 코드 변경을 제안했다.

이 결과가 중요한 이유는 간단하다.

> 좋은 에이전트는 코드를 잘 고치는 것뿐 아니라, 고칠 필요가 없을 때 아무것도 하지 않을 줄도 알아야 한다.

코드베이스도 이를 도와야 한다.

예를 들어 버그를 쉽게 재현할 수 있고, 관련 테스트가 명확하고, 현재 동작을 빠르게 확인할 수 있다면 에이전트가 괜히 손댈 가능성이 줄어든다.

책에서는 이것을 어려운 이름 대신 **"괜한 수정"**이라고 부른다.

---

## 2. 시키지 않은 것까지 건드린다

개발자가 "이 테스트 하나를 고쳐줘"라고 했는데 에이전트가 옆의 설정 파일까지 정리하는 경우가 있다.

그 변경 자체가 틀렸다는 뜻은 아니다. 문제는 **요청하지 않은 범위까지 일을 넓혔다는 것**이다.

2026년 OverEager-Bench는 이런 행동을 약 7,500번의 실행으로 조사했다. 연구에서는 코딩 에이전트가 단순한 작업에서도 관련 없는 파일을 삭제하거나 설정을 바꾸는 등 작업 범위를 넓히는 경우를 확인했다. 같은 모델이어도 어떤 실행 도구를 쓰느냐에 따라 차이가 컸다.

이 문제는 "코딩 실력이 부족하다"와 다르다.

오히려 일을 할 수 있기 때문에 생긴다.

Agentic Clean Code에서는 다음이 명확해야 한다.

- 이 기능은 어느 폴더가 담당하는가.
- 이 작업에서 건드리면 안 되는 영역은 어디인가.
- 공통 파일을 정말 바꿔야 하는가.
- 생성된 파일은 직접 수정하는 파일인가.
- 다른 모듈 변경이 필요한 경우 어떤 규칙을 따라야 하는가.

좋은 코드베이스는 에이전트에게 자유를 많이 주는 코드베이스가 아니라 **안전하게 움직일 수 있는 경계를 잘 보여주는 코드베이스**다.

---

## 3. 엉뚱한 곳을 고친다

버튼이 화면 밖으로 나가는 문제가 있다고 하자.

에이전트가 CSS에 한 줄을 추가해 문제를 없앴다. 테스트도 통과했다.

그런데 실제 원인은 공통 레이아웃 컴포넌트가 긴 문자열을 처리하지 못하는 것이었다면 어떻게 될까.

당장의 화면은 고쳐졌지만 같은 문제가 다른 화면에서 다시 나온다.

백엔드에서도 똑같다.

권한 검사가 잘못됐는데 Controller에서 조건문을 하나 추가할 수도 있다. 하지만 실제 규칙을 책임지는 곳이 Domain Service라면 잘못된 위치에 패치를 붙인 것이다.

SWE Atlas 같은 최근 평가에서는 코딩 에이전트가 단순히 패치를 만드는 능력보다 **기존 코드를 이해하고, 테스트를 제대로 쓰고, 구조를 유지하면서 리팩토링하는 능력**에서 여전히 어려움을 보인다고 보고한다. 2026년 결과에서도 가장 좋은 시스템조차 전체 평가에서 50%를 넘지 못했다.

따라서 좋은 코드베이스는 다음 질문에 답하기 쉬워야 한다.

> 이 규칙의 진짜 주인은 어디인가?

폴더 이름, 클래스 이름, 인터페이스, 테스트 위치, 의존 방향이 이 질문에 같은 답을 줘야 한다.

---

## 4. 필요한 코드를 덜 읽고 너무 빨리 고친다

코딩 에이전트가 빠르다고 항상 좋은 것은 아니다.

문제를 읽고 검색 한 번 한 뒤 가장 그럴듯한 파일을 바로 수정하는 경우가 있다.

작은 문제라면 맞을 수 있다. 하지만 실제 프로젝트에서는 한 기능이 여러 파일에 걸쳐 있을 수 있다.

예를 들어:

- API를 받는 곳
- 실제 규칙을 처리하는 곳
- DB에 저장하는 곳
- 다른 모듈이 사용하는 인터페이스
- 관련 테스트

가 따로 있을 수 있다.

여기서 해결책은 "항상 저장소 전체를 읽어라"가 아니다.

저장소 전체를 읽히면 느려지고, 필요 없는 정보가 많아지고, 오히려 판단이 흐려질 수 있다.

더 좋은 방향은:

> **하나의 변경에 필요한 코드가 가까이 모여 있고, 어디까지 읽어야 하는지 구조가 알려주는 것**이다.

기존 Clean Code가 함수와 클래스 안의 가독성을 중요하게 봤다면, Agentic Clean Code는 **작업에 필요한 범위가 얼마나 잘 모여 있는가**까지 본다.

---

## 5. 테스트는 통과했는데 제대로 고친 것은 아니다

코딩 에이전트에게 테스트는 아주 강한 신호다.

그래서 위험하기도 하다.

에이전트는 테스트를 통과하는 방향으로 코드를 바꾸는 데 능숙하다. 하지만 테스트가 문제의 일부만 보고 있다면 이상한 해결책도 통과할 수 있다.

2026년 SWE Refactor Bench에서는 기존 동작 테스트만 통과하면 실제 리팩토링을 하지 않고 예전 구현을 복사해서 남겨두는 식의 편법도 가능하다고 지적했다. 그래서 이 벤치마크는 "동작하는가"와 별도로 "실제로 마이그레이션이 끝났는가"를 따로 검사한다.

이 사례는 중요한 질문을 만든다.

> 테스트가 "결과가 맞다"만 확인하면 되는가?

Agentic Clean Code에서는 경우에 따라 다음도 검사해야 한다.

- 잘못된 의존성이 생기지 않았는가.
- 오래된 코드가 남아 있지 않은가.
- 금지된 API를 계속 사용하지 않는가.
- 공통 규칙을 우회하지 않았는가.
- 변경 범위가 필요 이상으로 커지지 않았는가.

즉 테스트는 정답 확인서만이 아니라 **에이전트가 엉뚱한 길로 가지 못하게 막는 가드레일**이 된다.

---

## 6. 각자 맞게 고쳤는데 합치면 깨진다

두 에이전트가 서로 다른 파일을 고쳤다고 하자.

Git 충돌도 없다.

그런데 한 에이전트는 사용자 상태가 세 종류라고 가정했고, 다른 에이전트는 같은 시간에 네 번째 상태를 추가했다.

두 코드 모두 각자 테스트에서는 통과할 수 있다. 합치면 문제가 생긴다.

이런 문제는 단순한 Git 충돌보다 어렵다.

겉으로는 다른 파일을 수정했기 때문이다.

2026년 CooperBench에서는 두 코딩 에이전트가 함께 작업할 때 단독으로 작업할 때보다 평균 성공률이 낮아지는 현상이 보고됐다. 단순히 에이전트끼리 메시지를 더 주고받게 한다고 문제가 완전히 해결되지도 않았다.

그래서 중요한 설계 원칙이 나온다.

> 에이전트끼리 자주 대화하게 만드는 것보다, 대화하지 않아도 안전하게 일할 수 있게 만드는 것이 먼저다.

공유 인터페이스나 데이터 형식이 바뀌면 관련 작업이 자동으로 깨져야 한다. 그래야 에이전트가 "내 코드만 보면 맞는데 왜 안 되지?"라는 상태에 빠지지 않는다.

---

## 7. 테스트가 가끔 거짓말한다

같은 코드를 두 번 실행했는데 한 번은 성공하고 한 번은 실패하는 테스트가 있다.

사람 개발자는 경험으로 "이거 원래 가끔 깨진다"라고 판단할 수 있다.

에이전트에게는 훨씬 어렵다.

에이전트는 실패를 보면 보통 자기 코드를 다시 수정한다.

그 결과:

- 정상 코드를 다시 고친다.
- 필요 없는 재시도를 한다.
- 관계없는 파일까지 보기 시작한다.
- 수정 범위가 커진다.

따라서 테스트가 빠른 것도 중요하지만 **믿을 수 있어야 한다.**

외부 네트워크, 현재 시간, 공유 DB, 다른 테스트가 남긴 파일 같은 것에 결과가 흔들리는 테스트는 Agentic 개발에서 특히 비싸다.

---

## 8. 오류는 났는데 어디가 문제인지 알 수 없다

아래 로그를 생각해보자.

```
500 Internal Server Error
Something went wrong
```

사람에게도 별 도움이 안 된다.

에이전트는 다시 로그를 찾고, stack trace를 읽고, 검색하고, 여러 파일을 열어야 한다.

반대로 이런 정보가 있다고 하자.

```
USER_PERMISSION_UPDATE_FAILED
작업: 사용자 권한 변경
규칙: 관리자는 최소 하나의 관리 권한을 가져야 함
관련 영역: user/permission
관련 테스트: USER-PERMISSION-07
```

한 번에 갈 수 있는 범위가 크게 줄어든다.

여기서 중요한 것은 로그를 길게 남기는 것이 아니다.

> **다음에 무엇을 봐야 하는지 알려주는 오류가 좋은 오류다.**

Agentic Clean Code에서는 오류 메시지도 코드 인터페이스의 일부로 본다.

---

## 9. 기존의 나쁜 코드를 그대로 따라 한다

코딩 에이전트는 저장소에 있는 코드를 참고한다.

이것은 큰 장점이면서 위험이기도 하다.

기존 코드에 잘못된 패턴이 많이 있으면 에이전트는 그것을 "이 프로젝트 방식"이라고 생각할 수 있다.

예를 들어:

- 모든 Service가 비대함
- 공통 Utils에 모든 로직이 들어감
- 예외를 전부 RuntimeException으로 던짐
- Controller에서 DB까지 직접 접근
- 비슷한 코드를 복사해서 사용

같은 구조가 이미 많으면 새 코드도 같은 방향으로 늘어나기 쉽다.

최근 대규모 연구에서도 AI가 작성한 실제 GitHub 변경에서 code smell, bug, security issue가 계속 관찰되고 일부는 이후 버전까지 남았다.

그래서 Agentic Clean Code에는 **청소가 한 번의 리팩토링 작업으로 끝나지 않는다**는 전제가 필요하다.

코드를 계속 만드는 Agent가 있다면, 나쁜 패턴을 계속 찾아 없애는 과정도 같이 필요하다.

---

## 10. 작업이 끝났다고 너무 빨리 판단한다

기능 하나를 구현한 뒤 테스트 하나가 통과하면 "완료"라고 판단하기 쉽다.

하지만 실제 완료에는 더 많은 것이 포함된다.

- 기존 기능이 깨지지 않았는가.
- 관련 문서나 설정은 맞는가.
- 필요 없는 코드가 남지 않았는가.
- 다른 사용 경로에서도 동작하는가.
- UI의 빈 화면, 오류 화면에서도 괜찮은가.
- 새로운 공통 의존성을 만들지는 않았는가.

SWE Atlas가 코드 수정뿐 아니라 코드 이해, 테스트 작성, 리팩토링을 따로 평가하는 것도 같은 이유다.

코드 한 번 생성하는 능력과 소프트웨어 변경을 끝까지 책임지는 능력은 같지 않다.

# 11. 지금까지 나온 실패를 한눈에 보면

| 실제로 보이는 문제 | 코드베이스가 도와줄 수 있는 것 |
|---|---|
| 고칠 필요가 없는데 손댐 | 쉽게 재현 가능한 테스트, 현재 동작 확인 |
| 시키지 않은 것까지 수정 | 담당 영역과 수정 경계 명확화 |
| 엉뚱한 곳에 패치 | 규칙의 주인과 의존 방향 명확화 |
| 너무 적게 읽고 수정 | 관련 코드 가까이 배치 |
| 테스트만 맞추는 편법 | 구조와 완료 조건도 자동 검사 |
| 따로는 맞는데 합치면 실패 | 명시적인 인터페이스와 호환성 검사 |
| 테스트가 가끔 실패 | 독립적이고 반복 가능한 테스트 |
| 오류 원인을 못 찾음 | 짧고 검색 가능한 오류 정보 |
| 나쁜 코드를 계속 복제 | 자동 구조 검사와 정기적인 정리 |
| 너무 빨리 완료 선언 | 단계별 완료 조건과 통합 검증 |

# 12. 여기서 나오는 Agentic Clean Code의 방향

이 실패들을 보고 나면 Agentic Clean Code가 무엇을 해야 하는지 조금 더 분명해진다.

좋은 코드는 단순히 사람이 읽기 좋은 코드가 아니다.

에이전트가:

1. **고칠지 말지 먼저 판단할 수 있고**
2. **어디를 봐야 하는지 빨리 찾을 수 있고**
3. **필요한 곳만 고칠 수 있고**
4. **다른 에이전트 작업을 망가뜨리지 않고**
5. **자기 수정이 맞는지 직접 확인하고**
6. **틀렸을 때 어디서부터 다시 봐야 하는지 알 수 있는 코드**

여기까지 포함해야 한다.
