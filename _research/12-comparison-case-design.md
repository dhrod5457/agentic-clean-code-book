# 같은 기능, 다른 코드베이스

작성일: 2026-10-03  
상태: 비교 사례 설계 v0.1

지금까지는 원칙을 만들었다.

이제부터는 그 원칙이 실제 코드에서 어떤 차이를 만드는지 보여줘야 한다.

다만 비교를 쉽게 만들기 위해 일부러 나쁜 코드를 만들지는 않는다.

예를 들어 이런 비교는 하지 않는다.

- 2,000줄짜리 Controller vs 잘 나눈 Service
- 변수명이 a, b, c인 코드 vs 의미 있는 이름
- 테스트가 하나도 없는 코드 vs 테스트가 있는 코드

이건 기존 Clean Code 책에서도 충분히 설명할 수 있다.

우리가 보고 싶은 것은 조금 다르다.

> **사람이 보기에는 둘 다 충분히 괜찮은 코드인데, Agent가 실제로 기능을 찾고 고치고 확인하고 병렬로 작업할 때 차이가 나는가?**

---

# 비교 사례 1. 회원 등급 규칙 하나 바꾸기

## 요구사항

> VIP 회원은 주문 금액이 10만 원 이상이면 무료 배송한다. 기존 15만 원 조건을 10만 원으로 바꿔라.

두 코드베이스 모두 테스트가 있고 클래스도 잘 나뉘어 있다고 가정한다.

## 구조 A

배송비 계산 규칙이:

- OrderService
- DeliveryPolicy
- PromotionService
- AdminOrderPreview
- BatchInvoiceJob

에 조금씩 들어 있다.

각 클래스만 보면 코드가 깨끗하다.

중복도 아주 심하지 않다.

문제는 "무료 배송 기준"이라는 하나의 규칙을 바꾸려면 어디까지 영향을 받는지 바로 알기 어렵다는 점이다.

Agent는 검색해서 15만원이라는 숫자를 찾는다.

몇 군데를 바꾼다.

그런데 BatchInvoiceJob은 금액을 상수로 쓰지 않고 별도 계산식을 사용해서 검색에 걸리지 않는다.

테스트 일부는 통과한다.

## 구조 B

무료 배송 조건의 기준은 DeliveryPolicy가 가진다.

다른 기능은 결과만 사용한다.

관리자 미리보기와 배치도 같은 정책을 호출한다.

Agent는:

1. DeliveryPolicy를 찾고
2. 테스트를 확인하고
3. 한 영역을 수정하고
4. 관련 테스트를 실행한다.

## 이 사례에서 볼 것

- 고칠 곳을 찾는 데 연 파일 수
- 실제 수정 파일 수
- 놓친 규칙이 있는지
- 수정 직후 실행할 테스트를 찾는 데 걸린 시간
- 기존 기능에 미치는 영향

## 이 사례가 보여주는 것

"코드를 잘 나눴다"와 "변경 이유에 맞게 나눴다"는 다르다.

# 비교 사례 2. 기능 하나 추가했는데 모두 같은 파일을 고친다

## 요구사항

서로 다른 Agent 10개에게 각각 다른 관리자 기능을 하나씩 추가하게 한다.

예:

- 휴면 회원 조회
- 환불 대기 조회
- 배송 지연 조회
- 쿠폰 만료 조회
- 미처리 문의 조회
- 비정상 로그인 조회
- 장기 미접속 조회
- 재고 부족 조회
- 결제 실패 조회
- 신고 누적 조회

## 구조 A

각 기능의 화면과 서비스는 독립적이다.

하지만 새로운 기능을 추가하면 반드시 다음 파일을 수정한다.

- AdminRoutes.ts
- AdminPermissions.ts
- AdminMenu.ts
- AdminApiRegistry.ts

사람 기준으로는 전체 기능을 한곳에서 보기 쉬운 구조다.

Agent 1개가 일할 때도 별문제 없다.

하지만 10개 Agent가 동시에 작업하면 모든 branch가 같은 파일 네 개를 건드린다.

## 구조 B

각 관리자 기능이 자기 module 안에서:

- route
- permission
- menu metadata
- API handler

를 선언한다.

전체 메뉴나 route 목록은 build 단계에서 모은다.

사람은 생성된 전체 목록을 볼 수 있지만 기능 추가 때 중앙 파일을 직접 수정하지 않는다.

## 이 사례에서 볼 것

- 같은 파일을 수정한 Agent 수
- Git conflict 수
- merge 후 수동 정리 시간
- 중앙 정보 확인이 더 어려워졌는지
- 자동 생성 방식의 복잡도가 어느 정도인지

## 중요한 점

구조 B가 항상 이긴다고 가정하지 않는다.

기능이 5개뿐인 작은 시스템에서는 구조 A가 더 단순할 수 있다.

책에서 보여주고 싶은 것은:

> 규모와 병렬 작업량이 커지면 "한곳에서 관리하기 쉬움"이 "모두가 같은 곳을 고침"으로 바뀔 수 있다는 점이다.

# 비교 사례 3. Controller에서 고쳐도 테스트는 통과한다

## 요구사항

> 탈퇴한 회원은 포인트를 사용할 수 없다.

## 구조 A

Controller에서 회원 상태를 확인한 뒤 PointService를 호출한다.

Agent가 버그를 받으면 Controller에 조건문을 추가한다.

API 테스트는 통과한다.

하지만 BatchPointUseJob은 Controller를 통하지 않는다.

배치에서는 탈퇴 회원이 계속 포인트를 쓸 수 있다.

## 구조 B

PointService의 실제 포인트 사용 규칙 안에서 회원 상태를 확인한다.

Controller와 Batch는 같은 규칙을 사용한다.

또 architecture test가:

> 포인트 사용 가능 여부는 PointPolicy 밖에서 따로 판단하지 않는다.

정도까지 강제할 수 있다면 더 좋다.

## 이 사례에서 볼 것

- 첫 수정 위치
- 테스트 통과 여부
- 다른 진입점에서의 동작
- Agent가 증상을 고쳤는지 규칙을 고쳤는지

## 이 사례가 보여주는 것

테스트 통과보다 중요한 질문이 있다.

> "이 규칙은 어디에서 책임져야 하는가?"

# 비교 사례 4. 화면 오류를 재현하기 위해 15번 클릭해야 한다

## 요구사항

> 부서명이 80자 이상이면 사용자 목록의 수정 버튼이 화면 밖으로 밀려난다.

## 구조 A

오류를 보려면:

1. 개발 서버 실행
2. 로그인
3. 관리자 메뉴 이동
4. 테스트 사용자 생성
5. 긴 부서명 입력
6. 저장
7. 사용자 목록으로 돌아감
8. 브라우저 폭을 줄임

Agent는 브라우저를 직접 조작하거나 fixture를 따로 만들어야 한다.

## 구조 B

UserList에 다음 상태가 이미 준비돼 있다.

- 기본
- 데이터 없음
- API 오류
- 긴 이름
- 긴 부서명
- 모바일 폭

Agent는 긴 부서명 상태를 바로 렌더링해 수정한다.

그 뒤 screenshot 비교로 확인한다.

## 이 사례에서 볼 것

- 오류 상태를 처음 재현하기까지 걸린 단계
- 실제 backend 필요 여부
- 사람의 수동 작업 필요 여부
- visual regression으로 검증 가능한지

## 이 사례가 보여주는 것

UI 코드는 화면이 예쁘게 나오는 것만으로 끝나지 않는다.

> 문제가 되는 화면 상태를 코드로 바로 만들어낼 수 있는가?

도 품질이다.

# 비교 사례 5. 테스트가 빠른데 믿을 수 없다

## 요구사항

> 주문 만료 시간을 30분에서 20분으로 바꿔라.

## 구조 A

테스트가 실제 현재 시간을 사용한다.

일부 테스트는 shared Redis를 사용한다.

평소에는 3초 만에 끝난다.

하지만 병렬 테스트나 실행 시점에 따라 가끔 실패한다.

Agent가 코드를 수정하고 테스트를 돌렸는데 실패한다.

자기 코드가 잘못됐다고 생각해 다시 수정한다.

## 구조 B

Clock을 주입하고, 테스트는 고정 시간을 사용한다.

Redis 대신 해당 테스트의 독립 fixture를 사용한다.

테스트 시간은 비슷하지만 같은 commit에서는 같은 결과가 나온다.

## 이 사례에서 볼 것

- 동일 commit에서 100회 반복 실패율
- Agent가 실패 뒤 불필요하게 바꾼 코드
- 재시도 횟수
- 최종 수정 범위

## 이 사례가 보여주는 것

빠른 테스트보다 중요한 것은:

> Agent가 그 결과를 믿어도 되는가?

# 비교 사례 6. 오류는 났지만 다시 처음부터 찾아야 한다

## 요구사항

운영에서 특정 주문의 환불이 실패한다.

## 구조 A

로그:

```
Failed to process request
IllegalStateException
```

stack trace는 여러 비동기 계층을 지난다.

Agent는:

- 로그 검색
- 주문 번호 검색
- 서비스 검색
- 상태 전이 검색
- 테스트 검색

을 반복한다.

## 구조 B

로그:

```
REFUND_STATE_INVALID
operation=refund.approve
orderId=...
currentState=SHIPPED
expected=REFUND_REQUESTED
module=refund
verification=refund-state-transition
```

민감 정보는 제외한다.

Agent가 바로 refund 상태 규칙과 관련 테스트로 갈 수 있다.

## 이 사례에서 볼 것

- 원인 파일을 찾기까지 검색 횟수
- 연 파일 수
- 수정하기 전 잘못 짚은 위치 수
- 문제 재현까지 걸린 명령 수

## 이 사례가 보여주는 것

오류 메시지는 단순 운영 로그가 아니다.

Agent가 다음 행동을 결정하는 입력이 된다.

# 비교 사례 7. 설명이 너무 많아 오히려 헷갈린다

## 요구사항

> 배송 조회 API에 선택 필드 하나를 추가해라.

## 구조 A

root AGENTS.md가 2,000줄이다.

- 모든 폴더 설명
- 과거 migration 역사
- frontend convention
- backend convention
- 운영 배포 방법
- DB 규칙
- 오래된 예외 규칙

을 모두 담고 있다.

Agent는 작업 시작 때 이 내용을 전부 받는다.

## 구조 B

root에는:

- 저장소 지도
- 공통 build/test
- 절대 어기면 안 되는 규칙
- 각 영역 문서 위치

만 있다.

배송 API 작업을 시작하면 shipping 영역의 짧은 문서를 추가로 읽는다.

## 이 사례에서 볼 것

- 첫 수정 전 사용한 입력량
- 관계없는 지침 수
- 실제 지침 위반 수
- task 수행 시간
- 결과 품질

## 이 사례가 보여주는 것

문서가 많다고 친절한 것이 아니다.

> 필요한 순간에 필요한 설명을 찾을 수 있는 것이 더 중요하다.

# 비교 사례 8. 이미 고쳐진 버그

## 요구사항

> 회원 탈퇴 후 프로필 이미지가 계속 노출된다. 수정하라.

실제로 현재 branch에서는 다른 작업으로 이미 수정된 상태다.

## 구조 A

이 상태를 빠르게 재현하는 테스트가 없다.

Agent는 issue 설명을 믿고 코드를 읽다가 비슷한 부분을 발견해 추가 조건을 넣는다.

## 구조 B

회원 탈퇴 시나리오를 바로 실행할 수 있다.

현재 테스트가 이미 통과한다.

Agent는 코드 변경 전에 현재 동작부터 확인하고:

> 현재 버전에서는 재현되지 않는다.

라고 끝낼 수 있다.

## 이 사례에서 볼 것

- 불필요한 production change 여부
- 작업 완료까지 수정 파일 수
- "변경 없음" 결론을 허용하는지

## 이 사례가 보여주는 것

좋은 코드베이스는 Agent가 많이 고치게 만드는 곳이 아니다.

필요 없으면 안 고치게 만드는 곳이다.

# 비교 사례 9. 첫 작업은 똑같이 성공하지만 다섯 번째부터 차이가 난다

이 사례가 중요하다.

Agentic Clean Code가 진짜 가치가 있으려면 첫 번째 task만 비교해서는 안 된다.

2026년 ChainSWE와 SWE-CI 같은 연구가 보는 것도 이 부분이다.

실제 소프트웨어는 한 번 수정하고 끝나지 않는다.

## 실험

같은 코드베이스에 순서대로 다섯 작업을 준다.

1. 회원 상태 추가
2. 상태별 권한 추가
3. 상태별 화면 표시 추가
4. batch 처리 추가
5. 상태 이름 변경

각 task 뒤의 repository를 그대로 다음 task에 넘긴다.

## 볼 것

- 1번째 task 성공률
- 3번째 task 성공률
- 5번째 task 성공률
- 변경 파일 수 증가
- 중복 증가
- 예외 규칙 증가
- 테스트 시간 증가
- 다음 Agent가 읽은 파일 수 증가

## 이 사례가 보여주는 것

Agentic Clean Code가 원하는 것은:

> "지금 한 번 잘 고친 코드"가 아니라 "계속 고쳐도 점점 어려워지지 않는 코드"다.

# 비교 사례 10. 16개 Agent를 동시에 넣어본다

마지막은 처음 문제의식으로 돌아간다.

16개 Agent에게 서로 다른 작업을 동시에 준다.

왜 바로 100개를 하지 않는가?

처음부터 100개를 돌리면 비용은 큰데 원인을 분석하기 어렵다.

2 → 4 → 8 → 16으로 늘리면서 어디서 충돌이 커지는지 보는 편이 낫다.

## 측정

- 같은 파일을 건드린 횟수
- merge conflict
- merge는 됐지만 테스트 실패
- 합친 뒤 별도 수정이 필요한 횟수
- Agent가 다른 Agent 결과를 기다린 횟수
- 전체 완료 시간

## 가장 중요한 결과

Agent 수가 늘어날 때:

### 구조 A

충돌과 통합 비용이 급격히 증가하는지

### 구조 B

증가폭이 더 완만한지

를 본다.

Agentic Clean Code의 병렬성 주장은 이 실험을 통과해야 한다.

---

# 실험 결과를 읽는 방법

한 지표로 승자를 고르지 않는다.

예를 들어 구조 B가:

- Agent는 더 잘 고치지만
- 사람이 읽기는 훨씬 어렵고
- build 구조가 복잡해지고
- 유지해야 할 generator가 크게 늘었다

면 무조건 좋은 설계가 아니다.

최소한 다음을 같이 본다.

| 질문 | 무엇을 확인하나 |
|---|---|
| 찾기 쉬운가 | 올바른 수정 위치까지 탐색량 |
| 좁게 고칠 수 있는가 | 변경 파일과 영향 영역 |
| 바로 확인 가능한가 | 첫 신뢰 가능한 검증까지 시간 |
| 같이 작업 가능한가 | Agent 수 증가에 따른 충돌 |
| 계속 유지 가능한가 | 여러 작업 후 복잡도 증가 |
| 사람에게도 좋은가 | 사람이 구조를 설명하고 리뷰하기 어려워지지 않는지 |

---

# 이 비교가 책에서 중요한 이유

책에서 원칙만 설명하면 독자는 이렇게 생각할 수 있다.

> "그냥 모듈화 잘하고 테스트 잘 만들라는 얘기 아닌가?"

맞는 부분이 있다.

그래서 차이를 코드 스타일이 아니라 **작업 과정**에서 보여줘야 한다.

같은 요구사항을 줬을 때:

- 어디부터 찾는지
- 몇 군데를 읽는지
- 어디를 고치는지
- 무엇으로 확인하는지
- 다른 Agent와 얼마나 부딪히는지
- 다음 작업이 더 쉬워지는지

가 달라지는 모습을 보여주는 것이 이 책의 핵심 실험이 된다.

# 추가 연구와 연결

최근 연구들도 단순 "최종 테스트 통과"에서 벗어나기 시작했다.

- NITR은 AI가 만든 repository 변경을 위치 선택, 재사용, 책임 분리, 의존성, 테스트 가능성, 상태 관리 같은 유지보수 관점에서 평가한다.
- SWE Atlas는 코드 이해, 테스트 작성, 리팩토링을 각각 평가한다.
- SWE Refactor Bench는 동작뿐 아니라 실제 구조 변경이 완료됐는지를 따로 확인한다.
- ChainSWE는 이전 수정 결과를 유지한 채 관련 버그를 연속으로 처리하게 한다.
- SWE-CI는 평균 233일, 71개 commit에 걸친 실제 repository 변화 흐름을 task로 구성한다.
- NL2Repo-Bench는 짧은 patch가 아니라 긴 시간 동안 하나의 repository를 만들어가는 능력을 본다.

이 흐름은 Agentic Clean Code가 "한 번의 코드 생성 품질"보다 **시간이 지나도 수정하기 좋은 repository**를 다뤄야 한다는 방향과 맞는다.
