# 첫 실험 계획 v0.1

작성일: 2026-10-03  
상태: 아직 구현하지 않음

비교 사례를 10개 만들었지만 처음부터 모두 구현하지 않는다.

먼저 가장 차이가 잘 드러나는 세 가지 실험만 만든다.

# 첫 번째 실험. 고칠 곳 찾기

## 질문

같은 기능을 두 구조로 만들었을 때 Agent가 올바른 수정 위치를 찾는 과정에 차이가 있는가?

## 작은 예제

주문 시스템.

기능:

- 주문
- 할인
- 배송
- 환불

버그:

> VIP 무료배송 기준이 잘못됐다.

### 구조 A

사람 기준으로는 충분히 정리돼 있지만 배송 규칙이 여러 사용처에 나뉘어 있다.

### 구조 B

정책의 책임이 한곳에 있고 사용처는 결과만 사용한다.

## 측정

- 올바른 파일을 찾기 전에 연 파일
- 검색 횟수
- 수정 파일
- 놓친 사용처
- 첫 성공 테스트까지 시간

# 두 번째 실험. 여러 Agent가 같이 고치기

## 질문

독립 기능을 동시에 추가할 때 중앙 수정 지점이 실제 충돌을 얼마나 만드는가?

## 작은 예제

관리자 대시보드.

8개의 독립 메뉴를 각각 다른 Agent에게 추가한다.

### 구조 A

모든 기능이 중앙 route/menu/permission registry를 수정한다.

### 구조 B

각 기능이 자기 metadata를 가지고 전체 목록은 자동으로 모은다.

## 측정

- 같은 파일 수정
- textual conflict
- merge 뒤 compile/test failure
- 수동 통합 수정
- 전체 완료 시간

# 세 번째 실험. UI 오류를 고치기

## 질문

화면 상태를 코드로 바로 재현할 수 있으면 Agent의 UI 수정 과정이 달라지는가?

## 작은 예제

사용자 관리 목록.

버그:

> 매우 긴 부서명이 들어오면 오른쪽 액션 버튼이 밀려난다.

### 구조 A

실제 앱을 실행하고 데이터를 만들어야 해당 화면을 볼 수 있다.

### 구조 B

long-department-name 상태를 바로 렌더링할 수 있다.

## 측정

- 오류를 처음 재현하기까지 단계
- backend 필요 여부
- browser interaction 횟수
- 성공한 수정까지 반복 횟수
- screenshot regression 결과

# 실험할 때 지켜야 할 것

## 1. 구조 A를 일부러 엉망으로 만들지 않는다

둘 다 사람이 작성한 정상적인 코드처럼 보여야 한다.

구조 A가 너무 나쁘면 결과가 정해진 실험이 된다.

## 2. 기능은 완전히 같아야 한다

사용자에게 보이는 동작, API, 데이터는 같게 만든다.

다른 것은 내부 구조와 검증 방법이다.

## 3. Agent에게 구조 차이를 알려주지 않는다

둘 다 동일한 task prompt를 준다.

"이쪽은 Agentic 구조입니다" 같은 힌트를 주지 않는다.

## 4. 같은 모델과 같은 조건을 사용한다

- 동일 모델
- 동일 thinking 설정
- 동일 timeout
- 동일 tool
- 동일 초기 instruction

## 5. 한 번만 실행하지 않는다

Agent 결과는 매번 조금씩 달라질 수 있다.

각 task/variant를 여러 번 반복한다.

초기에는 5회 정도로 패턴을 보고, 의미가 있으면 횟수를 늘린다.

## 6. 성공률만 보지 않는다

둘 다 성공해도 차이를 볼 수 있다.

예:

- A는 파일 17개를 읽고 성공
- B는 파일 5개를 읽고 성공

이것도 중요한 결과다.

# 기록 형식

각 실행마다 최소한 다음을 저장한다.

- model
- task
- variant
- start commit
- end commit
- 성공/실패
- 읽은 파일
- 수정한 파일
- 검색/명령 횟수
- 테스트 명령
- 첫 신뢰 가능한 테스트까지 시간
- 전체 소요 시간
- merge conflict 여부
- 최종 verifier 결과

가능하면 Agent의 자연어 답변보다 실제 tool/command 기록을 기준으로 측정한다.

# 아직 하지 않는 것

- 100 Agent 실행
- 거대한 실제 서비스 복제
- 특정 framework가 더 좋다는 결론
- Agentic Clean 점수 만들기
- 함수 길이 같은 임의 숫자 기준
- 실제 제품 코드에 바로 architecture rule 적용

첫 실험의 목적은 책의 주장이 측정 가능한지 확인하는 것이다.

---

# 성공 기준

실험 결과가 예상과 다르게 나와도 성공이다.

예를 들어:

> 중앙 registry 구조가 8 Agent 수준에서는 거의 문제가 없었다.

라는 결과가 나오면 책에서:

> "모든 중앙 파일을 없앨 필요는 없다. 병렬 작업량이 일정 수준을 넘어설 때 문제가 커진다."

라고 더 정확하게 쓸 수 있다.

좋은 결과를 증명하는 실험보다 **틀릴 수 있는 실험**을 만드는 것이 중요하다.
