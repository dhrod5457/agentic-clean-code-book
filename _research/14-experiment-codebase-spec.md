# A/B 실험용 코드베이스 설계서

작성일: 2026-10-03  
상태: 구현 전 설계 동결 후보

이 문서는 Agentic Clean Code의 주장을 시험하기 위한 작은 코드베이스를 어떻게 만들지 정한다.

목표는 "나쁜 코드와 좋은 코드"를 비교하는 것이 아니다.

두 코드베이스 모두 사람이 리뷰했을 때 충분히 괜찮아 보여야 한다.

차이는 하나다.

> 같은 요구사항을 받았을 때 Agent가 어디를 찾고, 얼마나 넓게 고치고, 어떻게 확인하고, 다른 Agent와 얼마나 부딪히는지가 달라지는가.

---

# 1. 공통 기능

두 구조는 기능이 완전히 같아야 한다.

작은 관리자용 업무 시스템을 사용한다.

도메인은 네 개만 둔다.

- 회원
- 주문
- 배송
- 환불

기능은 다음 정도로 제한한다.

## 회원

- 회원 조회
- 회원 상태 변경
- 회원 등급
- 탈퇴 처리

## 주문

- 주문 조회
- 주문 상태
- 주문 금액
- 주문 만료

## 배송

- 배송비 계산
- 무료배송 규칙
- 배송 상태

## 환불

- 환불 요청
- 환불 승인
- 환불 가능 상태 확인

## 관리자 UI

- 회원 목록
- 주문 목록
- 배송 목록
- 환불 목록

이 정도면 실제 서비스와 비슷한 관계를 만들 수 있으면서도 실험 결과를 분석하기 어렵지 않다.

---

# 2. 기술 선택 원칙

실험의 목적은 framework 비교가 아니다.

따라서 특별한 기술을 쓰지 않는다.

중요한 조건은 다음이다.

- 실행이 빠르다.
- 테스트가 빠르다.
- 구조 차이를 코드에서 쉽게 확인할 수 있다.
- UI state를 독립적으로 만들 수 있다.
- Agent가 일반적으로 익숙한 기술을 쓴다.
- 로컬에서 외부 서비스 없이 실행할 수 있다.

구현 기술은 다음 단계에서 확정한다.

이 문서에서는 특정 framework를 설계 원칙과 섞지 않는다.

---

# 3. Variant A와 Variant B의 공통 조건

A와 B는 다음이 같아야 한다.

## 기능

사용자에게 보이는 기능은 같아야 한다.

## API

요청과 응답 형식은 같아야 한다.

## 데이터

같은 fixture를 사용한다.

## 테스트 개수

완전히 같을 필요는 없지만 한쪽만 테스트가 훨씬 많은 구조는 피한다.

## 코드 품질

A에 일부러:

- 긴 함수
- 의미 없는 이름
- 거대한 클래스
- 복사 붙여넣기
- 주석 없는 복잡한 로직

을 넣지 않는다.

## 개발 편의

둘 다 정상적으로:

- build
- test
- lint
- local run

이 가능해야 한다.

---

# 4. Variant A의 성격

A는 흔히 볼 수 있는 "잘 정리된 일반 프로젝트"를 만든다.

Agent에게 불리하게 만들기 위해 일부러 이상하게 만들지 않는다.

대신 다음 특징은 허용한다.

## 4.1 레이어 중심 구조

예:

- controller
- service
- repository
- dto
- component
- pages

이 구조는 많은 프로젝트에서 정상적으로 사용한다.

하지만 하나의 기능을 고칠 때 여러 폴더를 오갈 수 있다.

## 4.2 공통 registry

다음과 같은 중앙 파일을 허용한다.

- route 목록
- 관리자 메뉴
- 권한 목록
- API 등록

사람이 전체 시스템을 한눈에 보는 데는 편하다.

## 4.3 일부 규칙은 여러 사용처에서 판단

예:

무료배송 기준을 DeliveryPolicy만 담당하지 않고:

- 주문 미리보기
- 실제 배송비 계산
- 배치 출력

등에서 각자 사용하도록 둘 수 있다.

단, 노골적인 복사 붙여넣기 수준으로 만들지는 않는다.

## 4.4 테스트는 기능별로 존재

테스트가 없는 프로젝트로 만들지 않는다.

다만 실제 수정 위치를 바로 알려주는 구조까지는 만들지 않는다.

## 4.5 UI는 실제 앱 흐름 중심

UI component test는 둘 수 있지만 모든 주요 상태를 독립 fixture로 만들지는 않는다.

---

# 5. Variant B의 성격

B는 지금까지 정리한 Agentic Clean Code 원칙을 적용한다.

## 5.1 기능 중심으로 찾을 수 있다

예:

```
member/
order/
delivery/
refund/
```

안에서 관련 규칙, 테스트, UI 상태를 찾을 수 있게 한다.

모든 코드를 한 폴더에 몰아넣는 뜻은 아니다.

해당 기능에서 어디를 봐야 하는지 예상 가능하게 만든다.

## 5.2 규칙의 주인을 하나로 둔다

예:

무료배송 여부는 DeliveryPolicy가 결정한다.

다른 곳에서는 같은 기준 금액을 따로 계산하지 않는다.

## 5.3 중앙 수정 지점을 줄인다

route, menu, permission 정보는 기능 가까이에 둔다.

전체 목록이 필요하면 자동으로 모은다.

사람이 전체 구조를 보는 방법은 유지한다.

## 5.4 중요한 약속은 자동으로 확인한다

예:

- 잘못된 module 의존
- 내부 API 직접 사용
- 순환 의존
- 금지된 접근

같은 것을 자동 검사한다.

## 5.5 빠른 검증과 전체 검증을 나눈다

수정한 기능은 몇 초 안에 확인할 수 있다.

완료 전에는 연결된 기능과 전체 상태도 검사한다.

## 5.6 UI 상태를 바로 만들 수 있다

예:

```
UserList / Default
UserList / Empty
UserList / Error
UserList / LongDepartmentName
```

처럼 실제 backend를 거치지 않고 문제 상태를 바로 만들 수 있게 한다.

## 5.7 오류가 관련 영역을 알려준다

generic error만 남기지 않는다.

예:

```
REFUND_STATE_INVALID
module=refund
verification=refund-state-transition
```

처럼 다음에 볼 곳을 좁힐 수 있게 한다.

---

# 6. 일부러 차이를 두면 안 되는 것

이 부분이 중요하다.

다음 요소가 다르면 실험이 깨진다.

## A만 더 복잡한 business rule을 갖게 하지 않는다

같은 기능이어야 한다.

## B만 더 좋은 이름을 쓰지 않는다

이름 품질은 둘 다 비슷하게 맞춘다.

## B만 테스트를 훨씬 많이 만들지 않는다

검증 구조는 달라도 test coverage 자체가 극단적으로 다르면 안 된다.

## B만 최신 framework를 사용하지 않는다

기술 stack 차이가 결과에 섞이면 안 된다.

## A만 일부러 느린 build를 만들지 않는다

실험에서 보고 싶은 것은 구조 차이다.

## Agent instruction을 다르게 주지 않는다

같은 task prompt를 사용한다.

---

# 7. 첫 실험에 필요한 상태

## 실험 1. 무료배송 기준 변경

초기 상태:

> VIP 무료배송 기준 = 150,000원

task:

> VIP 무료배송 기준을 100,000원으로 바꿔라.

A에서는 관련 판단이 여러 사용처에 걸쳐 있다.

B에서는 하나의 정책을 중심으로 사용한다.

---

## 실험 2. 관리자 기능 병렬 추가

초기 상태:

관리자 기능 4개 존재.

task:

8개 새로운 기능을 각각 독립 Agent에 배정.

A:

- 중앙 route
- 중앙 menu
- 중앙 permission
- 중앙 API registry

를 직접 수정.

B:

기능 내부 metadata를 추가하고 전체 목록은 자동으로 모음.

---

## 실험 3. 긴 부서명 UI 문제

초기 상태:

일반 부서명에서는 정상.

task:

> 부서명이 80자 이상일 때 버튼이 밀려난다. 수정하라.

A:

실제 화면 흐름을 거쳐 상태를 만들어야 함.

B:

long department fixture/story 존재.

---

# 8. 코드 크기

너무 작으면 차이가 안 난다.

너무 크면 실험 자체가 어려워진다.

초기 목표는 다음 정도다.

- backend: 작은 업무 프로젝트 수준
- frontend: 관리자 화면 4~6개
- test: 주요 기능별 기본 시나리오
- 파일 수: 수십~100개 초반 수준

정확한 숫자는 구현 전에 강제로 고정하지 않는다.

목표는 "toy example"처럼 보이지 않으면서도 실험 결과를 사람이 직접 검토할 수 있는 크기다.

---

# 9. 두 구조를 만드는 순서

실험 편향을 줄이기 위해 다음 순서로 만든다.

1. 공통 요구사항을 먼저 확정한다.
2. 공통 acceptance test를 만든다.
3. Variant A를 만든다.
4. Variant B를 만든다.
5. 두 구조가 같은 기능을 제공하는지 확인한다.
6. 실험용 task를 별도로 준비한다.
7. task 정답은 실험 branch 밖에 보관한다.

중요:

B를 먼저 만든 뒤 A를 일부러 나쁘게 역설계하지 않는다.

둘 다 공통 요구사항에서 독립적으로 설계한다.

---

# 10. 실험용 branch 원칙

각 실험은 같은 시작점에서 진행한다.

예:

```
experiment-a/base
experiment-b/base
```

각 Agent는 독립 worktree를 사용한다.

Agent의 변경이 다른 Agent에게 보이지 않게 한다.

병렬 실험에서는 마지막에 통합 전용 branch에서 merge한다.

---

# 11. Agent가 보게 되는 정보

Agent에게는 다음만 준다.

- task 설명
- 저장소 자체
- 저장소 안의 일반 개발 지침
- 실행 가능한 도구

주지 않는 것:

- A/B 구조의 목적
- 어느 쪽이 Agentic 구조인지
- 예상 수정 파일
- 연구 가설
- 정답 patch

이렇게 해야 Agent가 실험 의도를 보고 행동하지 않는다.

---

# 12. 사람 평가

모든 것을 자동 metric으로만 판단하지 않는다.

각 최종 diff는 사람이 다음 질문으로 검토한다.

- 요청한 것만 고쳤는가
- 실제 원인을 고쳤는가
- 필요 없는 변경이 들어갔는가
- 기존 구조를 더 어렵게 만들었는가
- 다음 수정자가 이해하기 어렵게 만들었는가

가능하면 A/B 정보는 가린 상태로 검토한다.

---

# 13. 실험에서 실패란 무엇인가

다음은 모두 별도로 기록한다.

- 기능 실패
- 테스트 실패
- 엉뚱한 위치 수정
- 요청 범위 초과
- 불필요한 변경
- merge conflict
- merge 뒤 기능 충돌
- flaky test로 인한 잘못된 재수정
- 완료 선언 후 hidden test 실패

성공/실패 하나로 끝내지 않는다.

---

# 14. 이 설계가 동결되기 전 확인할 것

다음 질문에 모두 답할 수 있어야 구현으로 넘어간다.

- A도 충분히 정상적인 프로젝트인가
- B가 단순히 test가 많아서 유리한 것은 아닌가
- A/B의 기능이 완전히 같은가
- 특정 framework가 결과를 결정하지 않는가
- task가 너무 쉽거나 너무 어렵지 않은가
- Agent가 실험 의도를 알아챌 정보가 없는가
- 사람이 결과를 재검토할 수 있는 규모인가

이 조건이 맞으면 그때 구현한다.
