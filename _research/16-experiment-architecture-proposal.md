# 실험용 프로젝트 구조 제안

작성일: 2026-10-03  
상태: 구현 전 승인용 설계안

이 문서는 실제 실험 코드를 만들기 직전의 구조 제안이다.

목표는 복잡한 샘플 서비스를 만드는 것이 아니다.

같은 기능을 가진 두 코드베이스를 만들고, Agent가 작업할 때 어떤 차이가 생기는지 관찰할 수 있어야 한다.

---

# 1. 프로젝트가 풀어야 하는 문제

실험은 다음 질문을 확인해야 한다.

1. Agent가 고칠 곳을 얼마나 빨리 찾는가.
2. 하나의 변경이 얼마나 넓게 퍼지는가.
3. 여러 Agent가 동시에 작업할 때 얼마나 자주 부딪히는가.
4. 수정 직후 얼마나 빨리 믿을 만한 결과를 확인할 수 있는가.
5. UI 오류를 사람 도움 없이 바로 재현할 수 있는가.
6. 여러 번 수정한 뒤에도 다음 Agent의 일이 쉬운가.

이 여섯 가지를 보기 위해 필요한 만큼만 만든다.

---

# 2. 전체 저장소 구조

하나의 저장소 안에 실험 코드와 연구 자료를 함께 두는 방향을 우선 제안한다.

예상 구조:

- 연구 문서
- 실험 공통 요구사항
- Variant A
- Variant B
- 공통 acceptance test
- 실험 task
- 실행 결과
- 분석 결과

A/B를 서로 다른 저장소로 나누지 않는 이유는 비교 기준과 실행 도구가 달라지는 것을 줄이기 위해서다.

단, 실제 Agent 실행 때는 각 variant를 독립 worktree에서 사용한다.

---

# 3. 기술 구성 제안

사용자에게 보이는 기능과 business rule이 중심이므로 너무 특이한 기술은 쓰지 않는다.

현재 우선안:

## Backend

Java 기반의 일반적인 웹 애플리케이션.

이유:

- 실제 업무 시스템과 비슷한 구조를 만들기 쉽다.
- Controller / Service / Domain / Repository 경계를 자연스럽게 비교할 수 있다.
- architecture rule과 테스트 도구가 충분하다.
- 실험 결과를 Java 개발자가 읽기 쉽다.

## Frontend

일반적인 component 기반 웹 UI.

이유:

- 관리자 목록 화면을 만들기 쉽다.
- UI state 비교가 쉽다.
- isolated state와 screenshot 검증 구조를 비교할 수 있다.

## Database

실험 기본 경로에서는 외부 DB 서버를 요구하지 않는다.

외부 DB 준비 시간이 Agent 실험 결과에 섞이지 않게 한다.

데이터 저장 자체보다:

- policy
- module
- test
- UI state

차이를 보는 것이 목적이다.

## 외부 API

기본 실험에서는 사용하지 않는다.

네트워크 상태가 결과를 흔들지 않게 한다.

---

# 4. Backend 책임

기능은 네 개다.

## Member

담당:

- 회원 조회
- 회원 상태
- 회원 등급
- 탈퇴

## Order

담당:

- 주문
- 주문 상태
- 주문 금액
- 주문 만료

## Delivery

담당:

- 배송비
- 무료배송
- 배송 상태

## Refund

담당:

- 환불 요청
- 환불 승인
- 환불 가능 상태

---

# 5. Variant A의 구조 방향

A는 레이어 중심의 일반적인 구조를 사용한다.

예상 개념:

- controller
- service
- repository
- dto
- config
- ui/pages
- ui/components

이 구조 자체를 나쁘다고 전제하지 않는다.

A의 핵심 특징은 다음이다.

### 기능을 찾을 때 여러 레이어를 오갈 수 있다

배송 기능 하나를 이해하려면:

- Controller
- Service
- DTO
- Repository
- UI

를 순서대로 찾아볼 수 있다.

### 전체 설정은 중앙에서 관리한다

예:

- route
- menu
- permission
- API registry

### 일부 business rule은 사용처 가까이에 있다

예:

무료배송 정책이 실제 계산과 관리자 미리보기에서 각각 판단될 수 있다.

단, 복사 붙여넣기처럼 노골적으로 나쁘게 만들지는 않는다.

### UI는 페이지 흐름 중심이다

오류 상태를 보기 위해 실제 화면으로 들어가야 하는 경우를 허용한다.

---

# 6. Variant B의 구조 방향

B는 기능을 중심으로 찾을 수 있게 한다.

예상 개념:

- member
- order
- delivery
- refund

각 기능 안에서:

- 공개 contract
- 규칙
- 사용 흐름
- 관련 테스트
- UI 상태

를 찾을 수 있게 한다.

### 내부 구현은 기능 안에 숨긴다

다른 기능은 공개된 약속만 사용한다.

### 중요한 규칙의 주인이 하나다

무료배송 판단은 한 정책이 담당한다.

다른 곳에서 같은 조건을 다시 만들지 않는다.

### 중앙 목록은 직접 수정하지 않는 방향을 우선한다

각 기능의 metadata를 모아 전체 route/menu 목록을 만든다.

### 중요한 경계는 자동으로 확인한다

예:

- 다른 기능의 내부 구현 직접 사용 금지
- 순환 의존 금지
- 공개되지 않은 API 사용 금지

### UI 상태를 바로 만들 수 있다

오류나 긴 문자열 상태를 실제 backend 없이 재현할 수 있다.

---

# 7. 공통 acceptance test

A/B 모두 같은 기능을 제공하는지 확인하기 위한 테스트다.

이 테스트는 어느 구조가 더 좋은지 평가하지 않는다.

오직 기능이 같은지만 본다.

예:

- VIP 무료배송
- 회원 탈퇴
- 주문 만료
- 환불 상태 전이
- 관리자 목록 조회

A만 실패하거나 B만 실패하면 구조 비교 전에 기능 차이부터 수정해야 한다.

---

# 8. Variant별 내부 테스트

A/B 내부 테스트는 구조에 따라 달라도 된다.

단, 기능 검증 수준은 비슷하게 맞춘다.

예를 들어 B에 architecture test가 있는 것은 허용한다.

그 자체가 Agentic 구조의 일부이기 때문이다.

하지만 B에만 business behavior test를 두 배로 넣는 식의 차이는 만들지 않는다.

---

# 9. UI 검증

UI 실험은 두 단계로 나눈다.

## 빠른 확인

특정 상태 하나를 바로 렌더링해 확인.

B에서는 이 경로가 준비돼 있다.

A에서는 실제 페이지 흐름을 거칠 수 있다.

## 최종 확인

둘 다 실제 application 기준으로 최종 화면이 맞는지 확인.

즉 B가 isolated state만 맞고 실제 화면은 깨진 상태가 되지 않게 한다.

---

# 10. 오류와 로그

A:

일반적인 예외와 stack trace를 사용한다.

일부 오류는 기능 이름 정도만 알 수 있다.

B:

오류에서 최소한 다음 중 일부를 바로 찾을 수 있게 한다.

- 작업 이름
- 기능 영역
- 깨진 규칙
- 재현할 테스트 또는 검증 방법

민감한 값은 어느 쪽에도 남기지 않는다.

---

# 11. 실험 실행 단위

하나의 실행은 다음으로 본다.

- 하나의 시작 commit
- 하나의 task
- 하나의 Agent
- 하나의 독립 workspace
- 하나의 최종 diff
- 하나의 실행 기록

병렬 실험에서는 여러 실행 결과를 마지막에 합친다.

---

# 12. 오류 처리 전략

실험 코드 자체에서도 오류를 숨기지 않는다.

기본 원칙:

- 예상 가능한 business 오류와 시스템 오류를 구분
- 오류를 삼키지 않음
- 테스트에서 실패 이유를 확인 가능하게 함
- 외부 환경 문제를 business failure처럼 보이지 않게 함

B에서는 여기에 "다음에 볼 곳을 줄여주는 정보"를 추가한다.

---

# 13. 데이터 검증 규칙

실험 task가 입력값 문제 때문에 흔들리지 않게 한다.

공통 규칙:

- 금액 음수 금지
- 필수 ID 누락 금지
- 회원/주문 상태는 정의된 값만 사용
- UI fixture도 동일한 데이터 규칙 사용

A/B의 validation 결과는 같게 한다.

---

# 14. 성능 기대

이 프로젝트는 부하 테스트용이 아니다.

중요한 성능은 처리량보다 개발 feedback 속도다.

우선 목표:

- 작은 기능 테스트는 즉시 결과를 확인할 수 있을 정도로 빠르게
- 전체 테스트도 반복 실험이 가능한 수준으로 유지
- UI 상태 실행도 별도 서버 준비를 최소화

정확한 초 단위 기준은 첫 구현 후 실제 측정값을 보고 정한다.

처음부터 숫자를 맞추기 위해 코드를 왜곡하지 않는다.

---

# 15. 보안 범위

실험 프로젝트라도 Agent 실행 환경은 실제 Agentic 개발 규칙을 일부 반영한다.

- 실제 비밀정보 사용 안 함
- production 접근 없음
- 외부 네트워크 의존 최소화
- Agent별 workspace 분리
- main 직접 변경 금지
- 실험 결과와 source 변경 분리

실제 운영 보안 시스템 전체를 재현하지는 않는다.

---

# 16. 테스트 접근

테스트는 네 단계로 생각한다.

## 1단계. 작은 단위 확인

방금 수정한 규칙이 맞는지 빠르게 확인.

## 2단계. 기능 확인

한 기능 전체가 맞는지 확인.

## 3단계. 연결 확인

다른 기능과 연결했을 때 문제없는지 확인.

## 4단계. 공통 acceptance

A/B가 사용자 관점에서 같은 기능을 제공하는지 확인.

UI는 여기에 화면 상태와 실제 사용자 흐름 검증이 추가된다.

---

# 17. 구현 전에 결정해야 할 것

실제 코드를 쓰기 전 아래 항목은 사용자 승인이 필요하다.

1. Backend를 Java 기반으로 갈 것인가.
2. Frontend 실험도 첫 구현부터 포함할 것인가.
3. A/B를 하나의 저장소 안에 둘 것인가.
4. 첫 실험을 세 개 모두 구현할 것인가, 하나부터 시작할 것인가.
5. 실제 Agent 실행은 어떤 도구/모델을 기준으로 할 것인가.

이 다섯 가지를 확정한 뒤 구현한다.
