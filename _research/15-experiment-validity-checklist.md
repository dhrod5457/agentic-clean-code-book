# 실험 결과를 믿기 위한 체크리스트

작성일: 2026-10-03

Agentic Clean Code를 주장하려면 실험 결과가 우리가 원하는 방향으로 나왔다고 좋아하면 안 된다.

실험 자체가 공정했는지를 먼저 확인해야 한다.

---

# 1. A를 일부러 나쁘게 만들지 않았는가

가장 큰 위험이다.

A가:

- 긴 함수
- 엉망인 이름
- 테스트 없음
- 순환 의존
- 복사 붙여넣기

로 가득하다면 B가 이기는 것은 당연하다.

그 실험으로는 Agentic Clean Code를 설명할 수 없다.

A는 일반적인 팀이 충분히 선택할 만한 구조여야 한다.

---

# 2. B가 단순히 테스트를 더 많이 가진 것은 아닌가

B가 테스트 200개, A가 30개라면 결과를 구조 차이라고 말하기 어렵다.

테스트의 역할은 달라도 기본적인 기능 검증 수준은 비슷하게 맞춘다.

---

# 3. Agent instruction은 같은가

한쪽에는:

> 관련 정책을 먼저 찾아라.

라고 적고 다른 쪽에는 아무 말도 안 하면 안 된다.

task prompt와 기본 Agent instruction은 동일하게 유지한다.

구조 자체가 Agent를 안내하는지를 보고 싶기 때문이다.

---

# 4. 같은 모델과 같은 도구인가

다음 조건을 기록한다.

- model
- version
- thinking level
- tool set
- timeout
- retry policy

도구가 다르면 결과 차이를 코드 구조 때문이라고 보기 어렵다.

---

# 5. 여러 번 반복했는가

같은 Agent도 실행마다 결과가 달라질 수 있다.

한 번의 성공과 실패로 결론 내리지 않는다.

초기:

- task당 5회

정도로 시작할 수 있다.

차이가 보이면 반복 횟수를 늘린다.

---

# 6. 성공률만 보지 않았는가

둘 다 100% 성공할 수 있다.

그래도 다음 차이가 중요하다.

- A는 파일 20개를 읽음
- B는 파일 6개를 읽음

- A는 파일 8개 수정
- B는 파일 2개 수정

- A는 테스트 결과까지 80초
- B는 8초

따라서 과정도 기록한다.

---

# 7. 사람에게 더 나쁜 구조가 되지 않았는가

B가 Agent에게는 좋지만 사람이 보기 어렵다면 문제가 있다.

별도 사람 리뷰에서:

- 구조 설명 가능성
- 변경 이유 이해
- diff 리뷰 난이도
- 새 개발자 onboarding 난이도

를 본다.

Agent 성능만으로 설계를 결정하지 않는다.

---

# 8. 생성 도구 자체가 새로운 부담을 만들지 않았는가

B에서 중앙 파일 충돌을 없애기 위해 generator를 추가했다고 하자.

그 generator가:

- 복잡함
- 자주 깨짐
- debugging 어려움
- build 느림

을 만든다면 이 비용도 포함해야 한다.

"Agent가 덜 충돌한다"만 보고 나머지 비용을 숨기지 않는다.

---

# 9. 실험 task가 실제 개발과 비슷한가

너무 인위적인 task는 피한다.

좋은 task:

- 정책 변경
- 필드 추가
- UI overflow
- 권한 변경
- API 상태 추가
- dependency 변경

같이 실제 업무에서 자주 나오는 변경이다.

---

# 10. 숨은 정답을 만들지 않았는가

Agent가 우리가 기대한 파일을 고치지 않았다는 이유만으로 실패로 처리하지 않는다.

다른 해결 방법도 실제로 맞을 수 있다.

판정은:

- 기능
- 구조
- 요청 범위
- 회귀
- 유지보수성

을 보고 한다.

---

# 11. 결과가 반대로 나와도 기록하는가

예:

> 중앙 registry가 8 Agent 수준에서는 거의 문제를 만들지 않았다.

이 결과도 그대로 남긴다.

그렇다면 책의 원칙을:

> 중앙 registry를 없애라.

가 아니라:

> 병렬 작업량이 커지고 동일 파일 수정이 반복되면 병목이 될 수 있다.

로 좁힌다.

실험은 책을 증명하기 위한 것이 아니라 책의 주장을 고치기 위한 것이다.

---

# 12. 실험 결과를 공개할 때 같이 보여줄 것

최종 결과에는 숫자만 싣지 않는다.

다음도 같이 남긴다.

- task 원문
- 시작 commit
- Agent 설정
- 실행 횟수
- raw result
- 실패 사례
- 최종 diff
- 판정 기준

그래야 독자가 결과를 다시 해석할 수 있다.

---

# 13. 실험을 중단해야 하는 경우

다음 상황이면 코드를 더 만들기 전에 설계를 다시 본다.

- A가 지나치게 불리함
- B가 framework 특성 때문에 유리함
- task가 너무 쉬워 둘의 차이가 없음
- task가 너무 어려워 둘 다 거의 실패
- 결과 변동이 너무 커 반복으로도 패턴이 안 보임
- metric 수집 방법이 실행 도구마다 달라 비교가 불가능

실험을 억지로 계속하지 않는다.

---

# 14. 최종 기준

이 실험에서 가장 중요한 질문은 하나다.

> 같은 기능을 가진 두 코드베이스 중 하나가 Agent에게 실제로 더 적은 탐색과 더 좁은 수정, 더 빠른 검증, 더 적은 충돌을 제공하는가?

그리고 그 차이가 사람에게 더 큰 복잡성을 떠넘기지는 않는가?

둘 다 만족해야 Agentic Clean Code라고 부를 수 있다.
