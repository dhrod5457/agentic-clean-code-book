# Agentic Clean Code 원칙 후보

작성일: 2026-10-03  
상태: 리서치 v0.1

이 문서는 지금까지 모은 실패 사례를 뒤집어서 만든 원칙 후보다.

어려운 용어를 새로 만드는 것이 목적은 아니다.

질문은 단순하다.

> 코딩 에이전트가 자주 이런 식으로 실패한다면, 코드는 어떻게 만들어야 실패가 줄어들까?

---

## 1. 고칠 곳이 보이게 만든다

에이전트가 버그 하나를 고치려고 저장소 전체를 뒤지게 만들지 않는다.

예를 들어 권한 문제가 생겼다면:

- 권한 규칙이 어디에 있는지
- 그 규칙을 누가 사용하는지
- 관련 테스트는 어디에 있는지

가 어느 정도 예상 가능해야 한다.

폴더 구조, 클래스 이름, 인터페이스, 테스트 위치가 서로 다른 답을 주면 에이전트는 헤맨다.

### 좋은 방향

- 기능별 책임이 분명하다.
- 이름만 보고도 역할을 어느 정도 알 수 있다.
- 관련 코드와 테스트가 가까이 있다.
- 같은 규칙을 여러 곳에서 따로 구현하지 않는다.

### 확인할 질문

> "사용자 권한 변경"이라는 작업을 받은 에이전트가 첫 몇 번의 검색 안에 제대로 된 영역을 찾을 수 있는가?

---

## 2. 한 작업은 가능한 한 한 영역에서 끝나게 한다

작은 요구사항 하나가 여러 모듈로 퍼지는 구조는 Agent에게 비싸다.

예를 들어 사용자 이름 규칙 하나를 바꾸는데:

- API
- 공통 Utils
- 관리자 화면
- 배치
- 통계
- 권한
- 검색

까지 전부 수정해야 한다면 서로 강하게 묶여 있는 것이다.

기존 Clean Code에서도 낮은 결합도를 중요하게 봤다.

Agent 시대에는 이유가 하나 더 생긴다.

> 변경 범위가 작을수록 여러 Agent가 동시에 작업하기 쉽다.

### 좋은 방향

- 기능의 주인이 명확하다.
- 다른 영역은 내부 구현이 아니라 공개된 약속만 사용한다.
- 작은 기능 추가 때문에 unrelated module을 수정하지 않는다.

### 확인할 질문

> 이 기능 하나를 고치기 위해 몇 개의 서로 다른 영역을 건드려야 하는가?

---

## 3. 모두가 건드리는 파일을 줄인다

새 기능을 추가할 때마다 꼭 수정해야 하는 파일이 있다.

예:

- 하나의 거대한 route 파일
- 중앙 registry
- 모든 권한을 담은 map
- 하나의 giant config
- 모든 타입을 넣은 공통 파일
- global stylesheet

사람 몇 명이 개발할 때는 관리가 편할 수 있다.

수십 개 Agent가 동시에 작업하면 이 파일이 병목이 된다.

2026년 GitHub Agent PR 연구에서는 서로 다른 Agent가 동시에 만든 PR 쌍에서 실제 Git textual conflict가 41.7% 발생했다. 같은 Agent가 만든 쌍에서는 19.8%였다.

텍스트 충돌만 본 결과이므로, 코드가 합쳐지지만 의미가 어긋나는 문제는 포함되지 않는다.

### 좋은 방향

- 새 기능은 새 파일 추가만으로 가능한 경우가 많다.
- module 내부에서 스스로 등록할 수 있다.
- 중앙 파일을 바꿔야 한다면 정말 중앙에서 관리해야 하는 정보인지 다시 본다.

### 확인할 질문

> 최근 기능 작업 20개에서 반복해서 등장하는 파일은 무엇인가?

이 질문 하나만으로도 숨은 병목을 많이 찾을 수 있다.

---

## 4. Agent끼리 대화하기 전에 코드로 약속을 남긴다

두 Agent가 서로 다른 파일을 고치더라도 같은 데이터 형식이나 인터페이스를 가정하고 있을 수 있다.

한쪽이 바꾸면 다른 쪽 코드도 영향을 받는다.

이 관계가 문서나 사람 머릿속에만 있으면 늦게 깨진다.

### 좋은 방향

약속을 가능한 한 코드로 표현한다.

- type
- interface
- schema
- API contract
- DB migration contract
- compatibility test
- architecture test

두 Agent가 서로 메시지를 주고받지 않아도 잘못된 가정을 하면 바로 실패하게 만든다.

### 확인할 질문

> 이 약속이 바뀌었을 때 관련 코드가 자동으로 실패하는가, 아니면 운영에서야 알게 되는가?

---

## 5. 중요한 규칙은 문서에만 쓰지 않는다

예를 들어 다음 규칙이 있다고 하자.

> Controller에서는 Repository를 직접 호출하지 않는다.

AGENTS.md나 개발 가이드에만 적어놓으면 Agent가 놓칠 수 있다.

가능하다면 빌드나 테스트가 바로 막아야 한다.

예:

- dependency rule
- architecture test
- lint
- type check
- schema validation

문서가 필요 없다는 뜻은 아니다.

문서는 "왜 이런 규칙이 있는지" 설명하고, 도구는 "어기면 바로 잡는 역할"을 한다.

### 확인할 질문

> 이 규칙을 처음 보는 Agent가 문서를 읽지 않아도 위반하면 바로 알 수 있는가?

---

## 6. 수정한 뒤 바로 확인할 수 있게 한다

에이전트가 코드 한 줄을 바꾼 뒤 결과를 확인하는 데 10분이 걸리면 작업 속도는 급격히 느려진다.

더 큰 문제는 전체 테스트만 있어서 실패 원인을 다시 찾아야 하는 경우다.

### 좋은 방향

- 기능 가까이에 빠른 테스트가 있다.
- 수정한 영역만 우선 검사할 수 있다.
- 전체 검사는 별도로 돌린다.
- 같은 코드는 반복 실행해도 같은 결과를 낸다.
- 실패 메시지가 짧고 구체적이다.

테스트를 많이 만드는 것이 목표가 아니다.

> 에이전트가 "내 수정이 맞나?"를 빠르고 믿을 수 있게 확인하게 만드는 것이 목표다.

### 확인할 질문

> 일반적인 작은 수정 후 첫 번째 믿을 만한 결과를 받는 데 몇 초가 걸리는가?

---

## 7. 테스트는 결과뿐 아니라 잘못된 길도 막아야 한다

테스트가 결과값만 보면 에이전트가 이상한 방식으로도 통과시킬 수 있다.

예를 들어 리팩토링 작업인데 옛 코드를 그대로 복사해 새 위치에 두어도 동작 테스트는 통과할 수 있다.

그래서 중요한 작업에는 구조적인 완료 조건도 필요할 수 있다.

예:

- 더 이상 옛 API를 사용하지 않는다.
- 금지된 package dependency가 없다.
- migration 대상 파일이 남아 있지 않다.
- 특정 module 밖에서 내부 클래스를 사용하지 않는다.

### 확인할 질문

> 테스트를 통과하면서도 요구사항의 의도를 피해서 구현할 방법이 있는가?

있다면 검증 방법이 부족한 것이다.

---

## 8. 오류가 다음에 볼 곳을 알려주게 한다

에이전트가 오류를 보고 다시 처음부터 검색하게 만들지 않는다.

좋은 오류는 다음 중 일부를 알려준다.

- 어떤 작업이 실패했는가
- 어떤 규칙이 깨졌는가
- 어느 기능 영역에서 났는가
- 관련된 식별자는 무엇인가
- 어떤 테스트로 다시 만들 수 있는가
- 상세 로그는 어디에 있는가

로그를 길게 만들자는 뜻이 아니다.

오히려 첫 화면에는 핵심만 보여주고 상세 정보는 필요할 때 보게 하는 편이 좋다.

### 확인할 질문

> 실패 메시지만 받은 Agent가 다음에 열어볼 파일이나 테스트를 예상할 수 있는가?

---

## 9. 사람이 클릭해야만 만들 수 있는 상태를 줄인다

특히 UI에서 중요하다.

버그를 보려면:

1. 로그인하고
2. 메뉴 세 개를 지나고
3. 특정 데이터를 만들고
4. 오류 API를 억지로 발생시키고
5. 화면 크기를 바꿔야 한다

면 Agent가 재현하기 어렵다.

UI 상태를 코드에서 직접 만들 수 있게 한다.

예:

- 정상
- 로딩
- 빈 화면
- 오류
- 권한 없음
- 긴 글자
- 일부 데이터 누락
- 모바일
- 느린 응답

브라우저 엔진이 필요 없다는 뜻이 아니다.

사람이 직접 브라우저를 돌아다니지 않아도 해당 상태를 바로 띄울 수 있어야 한다는 뜻이다.

### 확인할 질문

> 버그 리포트에 나온 화면 상태를 fixture나 story 하나로 바로 만들 수 있는가?

---

## 10. 설명은 많이 주는 것보다 필요한 곳에 둔다

Agent용 문서를 무조건 많이 작성하는 것도 답이 아니다.

2026년 AGENTS.md 연구에서는 repository context file이 평균적으로 성공률을 높이지 못했고, inference cost는 20% 이상 늘었다. 불필요한 요구사항이 오히려 일을 어렵게 만들 수 있었다.

그래서 root 문서 하나에 모든 것을 넣지 않는다.

### 좋은 방향

root에는:

- 저장소의 큰 구조
- 기본 build/test 방법
- 반드시 지켜야 하는 몇 가지 규칙
- 상세 문서 위치

정도만 둔다.

특정 기능의 규칙은 해당 기능 가까이에 둔다.

### 확인할 질문

> 이 작업과 관계없는 설명을 Agent가 얼마나 많이 읽어야 하는가?

---

## 11. 아무것도 바꾸지 않는 것도 정상적인 결과로 인정한다

에이전트에게 작업을 줬다고 반드시 코드가 바뀌어야 하는 것은 아니다.

- 이미 수정됐다.
- 재현되지 않는다.
- 요구사항이 현재 코드와 같다.
- 문제는 코드가 아니라 운영 설정이다.

이런 경우 "변경 없음"이 정답일 수 있다.

FixedBench에서는 코드 변경이 필요 없는 실제 task에서도 Agent가 불필요한 변경을 만드는 문제가 확인됐다.

### 좋은 방향

작업 흐름에 다음 결과를 허용한다.

- fixed
- no change needed
- cannot reproduce
- blocked by missing information

### 확인할 질문

> Agent가 코드를 한 줄도 바꾸지 않고도 작업을 성공적으로 끝낼 수 있는가?

---

## 12. Agent에게 필요한 만큼만 권한을 준다

코드 구조만 깨끗하면 충분하지 않다.

Coding Agent는 shell, filesystem, network, Git에 접근할 수 있다.

2026년 AuthBench 연구에서는 최신 모델도 필요한 권한과 불필요한 권한을 스스로 정확히 나누는 데 어려움을 보였다. 생각 시간을 늘린다고 이 문제가 자연스럽게 해결되지 않았다.

따라서 Agent가 스스로 안전한 권한을 정할 것이라고 기대하기보다 실행 환경이 경계를 만들어야 한다.

### 좋은 방향

- 작업별 isolated workspace
- 필요한 repository만 접근
- secrets는 workspace 밖에 둠
- production 접근 분리
- main 직접 수정 제한
- 필요한 network만 허용

이 부분은 코드 작성법보다는 Agentic 개발 환경 설계에 가깝지만, 책에서 빠뜨리면 안 된다.

### 확인할 질문

> 이 Agent가 실수했을 때 어디까지 망가뜨릴 수 있는가?

---

## 13. 다음 Agent가 이어서 하기 쉽게 남긴다

Agent가 작업하다 context가 끝날 수 있다.

다른 Agent가 이어받을 수도 있다.

따라서 중요한 상태가 한 Agent의 대화 속에만 있으면 안 된다.

남겨야 할 것은 긴 회고문이 아니다.

다음 Agent가 필요한 사실이다.

예:

- 어떤 문제를 확인했는가
- 무엇을 바꿨는가
- 무엇을 아직 못 했는가
- 어떤 테스트가 통과했는가
- 현재 branch/commit은 무엇인가

가능한 정보는 Git, test artifact, task state처럼 자동으로 남는다.

### 확인할 질문

> 지금 작업한 Agent가 사라져도 다른 Agent가 5분 안에 이어서 할 수 있는가?

---

## 14. 나쁜 패턴이 쌓이지 않게 계속 정리한다

에이전트는 기존 코드를 보고 프로젝트 스타일을 배운다.

따라서 나쁜 코드가 쌓이면 다음 Agent가 그것을 다시 따라 할 수 있다.

한 번의 대규모 리팩토링만으로는 부족하다.

### 좋은 방향

- 구조 위반을 자동으로 찾는다.
- 반복되는 중복을 관찰한다.
- 계속 커지는 파일을 찾는다.
- 공통 파일에 기능이 몰리는지 본다.
- 정기적으로 작은 정리를 한다.

### 확인할 질문

> 최근 3개월 동안 코드 구조는 조금씩 단순해지고 있는가, 아니면 예외가 계속 추가되고 있는가?

---

# 15. 후보를 그대로 책의 원칙으로 쓰지는 않는다

지금은 14개 후보다.

이대로 책에 넣으면 너무 많다.

서로 겹치는 것들이 있다.

예를 들어:

- "한 작업은 한 영역에서 끝나게 한다"
- "모두가 건드리는 파일을 줄인다"
- "Agent끼리 대화하기 전에 코드로 약속을 남긴다"

는 모두 **여러 Agent가 서로 덜 의존하게 만드는 설계**라는 큰 원칙 아래 묶을 수 있다.

또:

- "수정 뒤 바로 확인"
- "테스트가 잘못된 길도 막음"
- "오류가 다음에 볼 곳을 알려줌"

은 **Agent가 혼자 고치고 확인할 수 있는 피드백 구조**로 묶을 수 있다.

다음 문서에서는 이 14개를 책의 핵심 원칙 8개 정도로 압축한다.
