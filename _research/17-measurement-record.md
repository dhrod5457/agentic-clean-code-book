# 실험에서 무엇을 기록할 것인가

작성일: 2026-10-03  
상태: 측정 형식 초안

실험 결과를 믿으려면 Agent의 마지막 답변만 저장하면 안 된다.

"완료했습니다"보다 실제로 무엇을 했는지가 중요하다.

---

# 1. 실행 기본 정보

각 실행마다 기록한다.

- 실행 ID
- 날짜
- Variant A/B
- task 이름
- 시작 commit
- 사용 Agent
- 사용 모델
- 설정
- 최대 실행 시간

---

# 2. 찾는 과정

Agent가 실제 수정 위치를 찾기까지 기록한다.

- 검색 횟수
- 열어본 파일 수
- 처음 연 파일
- 처음 제대로 된 영역을 찾은 시점
- 잘못 짚은 파일 수

여기서 "제대로 된 파일"은 사전에 정답 하나를 고정하지 않는다.

최종 해결과 실제 규칙 책임을 보고 나중에 판단한다.

---

# 3. 수정 과정

- 수정 파일 수
- 새 파일 수
- 삭제 파일 수
- 공통 파일 수정 여부
- 다른 기능 영역 수정 여부
- 요청하지 않은 변경 여부

단순 line count만으로 평가하지 않는다.

---

# 4. 확인 과정

- 처음 실행한 테스트
- 첫 성공한 테스트
- 첫 믿을 만한 검증까지 시간
- 실행한 test command 수
- 실패 후 재시도 횟수
- flaky failure 여부
- 최종 acceptance 결과

UI:

- 화면 상태 재현까지 단계
- browser interaction 횟수
- screenshot 비교 여부
- 실제 앱 최종 확인 여부

---

# 5. 병렬 작업

병렬 실험에서는 추가로 기록한다.

- 동시 Agent 수
- 같은 파일을 수정한 Agent 쌍
- Git conflict
- merge는 됐지만 test 실패
- 합친 뒤 추가 수정
- 다른 Agent 작업을 기다린 횟수

---

# 6. 결과 품질

자동 검증:

- 기능 통과
- architecture rule 통과
- regression 통과
- UI 검증 통과

사람 검토:

- 실제 원인을 고쳤는가
- 요청 범위를 지켰는가
- 필요 없는 변경이 있는가
- 다음 수정이 더 어려워졌는가
- 코드가 사람에게도 이해 가능한가

---

# 7. 연속 변경 실험

같은 repository를 계속 수정할 때는 task별 값뿐 아니라 변화도 본다.

예:

Task 1:
- 읽은 파일 5
- 수정 파일 2

Task 5:
- 읽은 파일 17
- 수정 파일 7

이렇게 시간이 지날수록 작업 범위가 커지는지 본다.

추적할 것:

- 평균 읽은 파일 수
- 평균 수정 파일 수
- 테스트 시간
- 공통 파일 수정 빈도
- architecture violation
- 중복 증가
- Agent 실패율

---

# 8. 결과를 한 점수로 합치지 않는다

Agentic Clean Score 같은 하나의 점수를 만들지 않는다.

예를 들어:

- 찾기는 빠른데
- 테스트가 느리고
- 병렬 충돌은 적고
- 사람이 읽기는 어려울 수 있다.

이걸 82점 하나로 만들면 중요한 차이가 사라진다.

결과는 여러 축으로 보여준다.

---

# 9. 책에서 보여줄 기본 표

실험 결과는 이런 형태가 이해하기 쉽다.

| 항목 | A | B |
|---|---:|---:|
| 고칠 곳 찾기 전 연 파일 |  |  |
| 최종 수정 파일 |  |  |
| 첫 검증까지 시간 |  |  |
| 전체 검증 시간 |  |  |
| 잘못 수정한 파일 |  |  |
| 요청 밖 변경 |  |  |
| 병렬 충돌 |  |  |
| 사람 리뷰 문제 |  |  |

여기에 실제 diff와 Agent 행동을 짧게 같이 보여준다.

---

# 10. 중요한 것은 숫자보다 이유

예를 들어 B가 파일을 더 많이 읽었다고 해서 바로 실패한 설계는 아니다.

왜 더 읽었는지를 본다.

- 관련 계약을 확인하느라 읽었는가
- 구조가 흩어져 있어서 헤맸는가
- architecture rule을 확인하느라 읽었는가

숫자는 현상을 찾는 신호다.

판단은 실제 작업 흐름과 함께 한다.
