# 책 문체와 설명 원칙

작성일: 2026-10-03

이 책은 논문처럼 쓰지 않는다.

연구 자료는 충분히 조사하되, 독자는 새로운 학술 용어를 배우러 온 사람이 아니라 **AI 코딩 도구를 실제 개발에 어떻게 맞춰야 하는지 이해하려는 개발자**라고 가정한다.

## 기본 원칙

### 1. 현상부터 말한다

나쁜 예:

> Agent의 Wrong Localization과 Semantic Conflict를 줄여야 한다.

좋은 예:

> 에이전트가 문제의 진짜 원인이 아닌 곳을 고치는 경우가 있다. 각자 다른 파일을 잘 고쳤는데 합치면 깨지는 경우도 있다.

현상을 설명한 뒤 필요할 때만 용어를 붙인다.

---

### 2. 영어 용어를 제목으로 남발하지 않는다

연구 단계에서는 정확한 검색을 위해 영문 용어를 남길 수 있다.

본문에서는 가능한 한 다음처럼 쓴다.

| 연구 용어 | 본문 표현 |
|---|---|
| Localization Cost | 고칠 곳을 찾는 데 드는 비용 |
| Change Blast Radius | 하나를 고쳤을 때 영향을 받는 범위 |
| Hot File | 여러 작업이 계속 같이 건드리는 파일 |
| Semantic Conflict | 파일 충돌은 없지만 의미가 충돌하는 문제 |
| Context Efficiency | 필요한 코드만 얼마나 잘 찾아 읽는가 |
| Diagnosability | 문제가 났을 때 원인을 얼마나 빨리 찾을 수 있는가 |
| Hermetic Test | 외부 환경에 흔들리지 않는 테스트 |
| Action Bias | 고칠 필요가 없는데도 뭔가 바꾸려는 경향 |
| Scope Expansion | 시키지 않은 것까지 건드리는 문제 |
| Entropy | 코드가 조금씩 어지러워지는 현상 |

---

### 3. 정의보다 예시를 먼저 쓴다

나쁜 순서:

> Change Coupling이란 두 파일이 반복적으로 함께 변경되는 현상을 뜻한다.

좋은 순서:

> 서로 import하지도 않는 두 파일이 있다. 그런데 기능 하나를 바꿀 때마다 항상 둘을 같이 고쳐야 한다. 코드만 보면 관계가 없어 보이지만 실제 개발에서는 강하게 묶여 있는 셈이다. 이런 관계를 연구에서는 change coupling이라고 부른다.

---

### 4. 숫자는 의미와 함께 쓴다

나쁜 예:

> 성공률이 30% 감소했다.

좋은 예:

> 두 에이전트에게 일을 나눠줬더니, 혼자 전체 작업을 했을 때보다 오히려 성공률이 평균 30% 정도 낮아졌다. 에이전트 수를 늘린다고 자동으로 개발이 빨라지는 것은 아니었다.

---

### 5. 한 문장에 개념을 여러 개 넣지 않는다

나쁜 예:

> Agentic architecture는 locality, observability, determinism, diagnosability와 parallel changeability를 확보해야 한다.

좋은 예:

> 에이전트가 필요한 코드를 빨리 찾을 수 있어야 한다. 테스트 결과는 매번 같아야 한다. 문제가 생기면 원인을 바로 좁힐 수 있어야 한다. 여러 에이전트가 동시에 작업해도 서로 영향을 덜 줘야 한다.

뒤에서 필요하면 네 가지 원칙으로 정리한다.

---

### 6. 새로운 이름을 만드는 데 신중한다

책의 차별화를 위해 모든 현상에 이름을 붙이지 않는다.

새 용어는 다음 조건을 만족할 때만 만든다.

- 기존 용어로 설명하기 어렵다.
- 책 전체에서 반복해서 사용한다.
- 실제 설계 판단에 도움이 된다.
- 측정하거나 비교할 수 있다.

현재 강하게 남길 후보:

- Agentic Clean Code
- Task Surface

나머지는 가능한 한 평범한 한국어로 설명한다.

---

### 7. "무조건"이라는 표현을 피한다

Agent 모델과 도구는 빠르게 바뀐다.

따라서:

- 함수는 반드시 N줄 이하여야 한다.
- 파일은 반드시 N개 이하를 읽어야 한다.
- 모든 프로젝트는 100 Agent 병렬 작업을 지원해야 한다.

같은 규칙은 만들지 않는다.

대신 왜 그런 방향이 필요한지, 어떤 조건에서 도움이 되는지를 설명한다.

---

### 8. 기존 Clean Code를 허수아비로 만들지 않는다

"Clean Code는 끝났다"는 문제 제기는 사용할 수 있다.

그러나 본문에서는 기존 Clean Code가 틀렸다고 몰아가지 않는다.

더 정확한 흐름은:

> Clean Code가 풀려고 했던 문제는 여전히 중요하다. 다만 코드를 읽고 고치는 주체가 달라졌다. 그래서 우리가 깨끗하다고 부르는 범위도 넓어져야 한다.

---

### 9. 현업 장면을 계속 사용한다

가능하면 모든 장은 실제 개발 상황으로 시작한다.

예:

> "사용자 목록의 버튼이 잘린다. 고쳐줘."

이 한 문장을 받은 Agent가:

- 어디부터 찾는지
- 몇 파일을 읽는지
- 화면을 어떻게 재현하는지
- 무엇을 수정하는지
- 어떻게 검증하는지

를 따라가며 설명한다.

독자는 이 과정을 통해 원칙을 이해한다.

---

### 10. 논문 이름은 본문 흐름을 깨지 않게 한다

본문:

> 실제 연구에서도 이미 고쳐진 문제를 받은 코딩 에이전트가 불필요한 변경을 만드는 경우가 자주 관찰됐다.

각주/출처:

> FixedBench, 2026

연구 제목과 저자를 본문마다 반복해서 나열하지 않는다.

---

## 이 책의 기본 목소리

- 개발자가 실제 프로젝트를 해보면서 발견한 문제를 설명하는 느낌
- 과장하지 않음
- AI를 신기한 기술처럼 떠받들지 않음
- 기존 개발자를 가르치려 들지 않음
- 어려운 용어보다 실제 코드와 작업 흐름을 우선
- 결론을 억지로 반복하지 않음
- 각 장에서 "그래서 구현할 때 무엇을 바꿔야 하는가"까지 연결

## 한 문장 기준

> 연구는 깊게 하고, 설명은 쉽게 한다.
