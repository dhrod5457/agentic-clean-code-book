# Agentic Clean Code 핵심 원칙 v0.2

작성일: 2026-10-03  
상태: 반론 검토 후 수정본

v0.1의 8개 원칙을 일부러 반박해봤다.

결론부터 말하면 8개 축은 아직 유효하다.

대신 몇몇 원칙을 잘못 읽으면:

- 코드가 지나치게 잘게 쪼개지고
- 중앙 기준까지 없애고
- 테스트를 너무 local하게 만들고
- 규칙을 과도하게 자동화하고
- Agent를 위해 사람이 읽기 어려운 코드를 만드는

반대 결과가 생길 수 있었다.

그래서 표현을 수정한다.

---

# 1. 필요한 코드로 가는 길을 분명하게 만든다

목표는 파일을 무조건 작게 만드는 것이 아니다.

큰 파일 하나가 흐름을 한눈에 보여줄 때도 있다.

반대로 10줄짜리 파일 50개를 오가야 한다면 오히려 이해하기 어렵다.

좋은 구조는 문제 하나를 받았을 때 **어디부터 보고, 어디까지 보면 되는지 예상할 수 있는 구조**다.

확인 질문:

> 이 기능을 처음 보는 사람이나 Agent가 불필요한 파일을 많이 열지 않고 담당 코드를 찾을 수 있는가?

---

# 2. 실제 변경 이유에 맞게 경계를 나눈다

Agent를 병렬로 돌리기 위해 억지로 모든 것을 분리하지 않는다.

같이 바뀌는 코드는 가까이 있는 것이 자연스럽다.

서로 다른 이유로 바뀌는 코드가 상대방의 내부 사정을 알아야 하는 구조가 문제다.

배포 단위를 나누는 것과 코드의 변경 경계를 나누는 것도 구분한다.

Microservice가 아니어도 하나의 애플리케이션 안에서 충분히 좋은 경계를 만들 수 있다.

확인 질문:

> 이 두 코드가 같이 있는 이유가 정말 같은 이유로 바뀌기 때문인가?

---

# 3. 여러 작업이 같은 수정 지점으로 몰리지 않게 한다

중앙 기준이 나쁜 것이 아니다.

전체 구조를 한눈에 보여주는 파일도 필요할 수 있다.

문제는 새 기능을 만들 때마다 모든 Agent가 같은 파일을 직접 편집해야 하는 구조다.

가능하면:

- 각 기능이 자기 정보를 가지고
- 전체 목록은 자동으로 모으거나
- 중앙 파일이 자주 바뀌지 않게

만든다.

확인 질문:

> 서로 상관없는 기능 작업들이 반복해서 같은 파일을 수정하고 있지 않은가?

---

# 4. 오래 유지할 중요한 약속은 자동으로 확인한다

모든 설계 취향을 lint로 만들지는 않는다.

정말 깨지면 안 되는 규칙을 고른다.

예:

- 의존 방향
- 공개 API 경계
- 데이터 형식
- 보안 규칙
- 호환성
- 순환 의존성

기계는 바닥선을 지킨다.

좋은 설계인지 판단하는 일까지 대신하지 않는다.

확인 질문:

> 이 규칙은 1년 뒤에도 유지돼야 할 약속인가, 지금 팀이 선호하는 방식일 뿐인가?

---

# 5. 가까운 곳에서 빠르게 확인하고, 마지막에는 합쳐서 확인한다

Agent가 한 줄을 바꿀 때마다 전체 테스트를 돌릴 필요는 없다.

반대로 local test만 통과했다고 작업이 끝난 것도 아니다.

검증을 단계로 나눈다.

> 수정한 곳 → 연결된 곳 → 합쳐진 결과 → 필요한 경우 전체

UI도 같은 방식이다.

특정 오류 화면은 바로 재현할 수 있어야 하지만 실제 사용자 흐름 전체 검사도 필요하다.

확인 질문:

> 수정 직후에는 빨리 확인할 수 있고, 완료 전에는 실제 연결 상태까지 확인하는가?

---

# 6. 오류는 다음에 볼 곳을 알려주게 한다

로그를 많이 남기는 것이 목적이 아니다.

첫 번째 오류 정보가 다음 행동을 줄여줘야 한다.

예:

- 무엇이 실패했는지
- 어떤 규칙과 관련 있는지
- 어느 기능에서 났는지
- 어떤 테스트로 다시 만들 수 있는지
- 상세 정보는 어디에 있는지

민감한 데이터는 남기지 않는다.

확인 질문:

> 이 오류를 처음 본 사람이나 Agent가 다음 검색 한 번을 줄일 수 있는가?

---

# 7. 필요한 특별한 정보와 필요한 권한만 준다

문서를 짧게 만드는 것 자체가 목표는 아니다.

프로젝트만의 특별한 사실은 충분히 알려줘야 한다.

대신 모델이 이미 알거나 코드와 도구가 직접 알려주는 내용을 장황하게 반복하지 않는다.

권한도 마찬가지다.

작업에 필요한 권한은 줘야 하지만 "혹시 필요할 수도 있으니까" 모든 권한을 주지는 않는다.

확인 질문:

> 지금 제공하는 정보와 권한 중 이 작업에 필요 없는 것은 무엇인가?

---

# 8. 현재 작업을 좁게 끝내되 다음 작업을 더 어렵게 만들지 않는다

"다음 Agent를 위해 정리한다"는 이유로 주변 코드를 마음대로 리팩토링하지 않는다.

먼저 현재 작업의 범위를 지킨다.

그 안에서:

- 새 중복을 만들지 않고
- 새 예외 규칙을 만들지 않고
- 기존 구조를 더 흐리지 않고
- 필요한 테스트와 상태를 남긴다.

더 큰 정리가 필요하면 별도의 작업으로 분리한다.

확인 질문:

> 이 변경은 요청 범위를 지키면서도 다음 수정자의 일을 더 어렵게 만들지는 않았는가?

---

# 9. 8개 원칙 위에 있는 세 가지 기준

개별 원칙보다 이 세 가지가 더 중요할 수 있다.

## 기준 A. 사람에게 나빠지면 다시 생각한다

Agentic Clean Code는 사람이 읽는 코드를 포기하는 방법론이 아니다.

Agent 때문에 사람이 이해하기 어려워지는 구조라면 다른 방법을 찾아야 한다.

## 기준 B. 모델의 현재 약점에 맞춰 설계하지 않는다

"현재 모델이 파일 20개부터 힘들어한다" 같은 이유로 영구적인 아키텍처 규칙을 만들지 않는다.

모델은 바뀐다.

코드 자체에서 생기는 문제에 집중한다.

## 기준 C. 숫자를 규칙으로 만들기 전에 실제 저장소에서 잰다

- 파일은 N줄 이하
- Agent는 N개 파일 이하로 읽어야 함
- 변경 파일은 N개 이하

같은 고정 숫자를 책에서 제시하지 않는다.

먼저 실제 프로젝트의:

- 평소 변경 범위
- 자주 같이 바뀌는 파일
- 테스트 시간
- 충돌 위치
- 오류 탐색 시간

을 측정한다.

좋고 나쁨의 기준은 프로젝트마다 다를 수 있다.

---

# 10. v0.2의 가장 짧은 설명

8개를 모두 외울 필요는 없다.

더 짧게 말하면 네 가지다.

> **찾기 쉽다.**  
> **좁게 고칠 수 있다.**  
> **바로 확인할 수 있다.**  
> **다음 작업을 망치지 않는다.**

나머지 원칙은 이 네 문장을 실제 코드베이스에 적용하기 위한 방법이라고 볼 수 있다.

이 네 문장이 책의 상위 구조로 쓸 수 있는지는 다음 단계에서 검토한다.

---

# 11. 현재 책의 중심 문장 후보

> 예전에는 좋은 코드를 "사람이 읽고 고치기 쉬운 코드"라고 설명했다. 이제는 하나를 더 봐야 한다. Agent가 고칠 곳을 찾고, 필요한 만큼만 바꾸고, 자기 결과를 확인하고, 다른 작업과 부딪히지 않게 만들 수 있는가. Agentic Clean Code는 이 질문에서 시작한다.

그리고 더 짧게:

> **Agentic Clean Code는 찾기 쉽고, 좁게 고칠 수 있고, 바로 확인할 수 있고, 다음 작업을 망치지 않는 코드다.**

아직 최종 문구는 아니다.
