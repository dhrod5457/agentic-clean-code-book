# Agentic Clean Code 핵심 원칙 v0.1

작성일: 2026-10-03  
상태: 아직 집필 목차가 아니라 연구 결과를 압축한 초안

앞 문서에서는 실패 사례에서 14개의 원칙 후보를 만들었다.

하지만 책에서 14개의 규칙을 외우게 만들고 싶지는 않다.

비슷한 내용을 합치면 지금 단계에서는 8개 정도가 남는다.

---

# 원칙 1. 고칠 곳을 찾기 쉽게 만든다

좋은 코드는 읽기 쉬워야 한다.

Agent 시대에는 하나가 더 필요하다.

**어디를 읽어야 하는지도 찾기 쉬워야 한다.**

버그 하나를 고치는데 저장소 전체를 뒤져야 한다면 함수 하나하나가 아무리 깔끔해도 작업은 어렵다.

관련 코드, 테스트, 데이터 형식이 어느 정도 같은 영역에 모여 있어야 한다.

폴더 이름과 코드 책임도 맞아야 한다.

이 원칙이 해결하려는 문제:

- 엉뚱한 곳을 고침
- 너무 적게 읽고 수정함
- 저장소 전체를 불필요하게 탐색함

독자에게 던질 질문:

> 이 문제를 처음 보는 개발자나 Agent가 고칠 곳을 얼마나 빨리 찾을 수 있는가?

---

# 원칙 2. 하나를 고쳤을 때 다른 곳이 덜 흔들리게 만든다

코드가 서로 너무 많이 연결돼 있으면 작은 변경도 여러 곳으로 퍼진다.

사람에게도 불편하지만 여러 Agent가 동시에 일할 때는 더 큰 문제가 된다.

Agent A가 사용자 기능을 고치는데 Agent B의 결제 기능까지 영향을 받으면 병렬 작업의 의미가 줄어든다.

그래서 기능의 내부 사정은 가능한 한 그 기능 안에 머물게 하고, 다른 영역은 공개된 인터페이스만 사용하게 한다.

이 원칙이 해결하려는 문제:

- 수정 범위가 계속 커짐
- Agent 작업끼리 서로 기다림
- 예상하지 못한 다른 기능이 깨짐

독자에게 던질 질문:

> 이 기능을 바꾸면 관계없는 기능도 같이 고쳐야 하는가?

---

# 원칙 3. 여러 작업이 같은 파일로 몰리지 않게 한다

모듈이 잘 나뉘어 있어도 기능을 추가할 때마다 하나의 중앙 파일을 수정해야 한다면 실제 병렬성은 낮다.

예:

- 거대한 registry
- 전역 route 파일
- 공통 permission map
- giant config
- 하나의 global stylesheet

이런 파일은 여러 Agent가 동시에 일할 때 교차로처럼 막힌다.

새 기능이 기존 파일을 계속 수정하기보다 자기 영역 안에서 추가될 수 있는 구조가 좋다.

이 원칙이 해결하려는 문제:

- merge conflict
- Agent 대기
- 공통 파일 비대화
- 기능 추가가 많아질수록 통합 비용 증가

독자에게 던질 질문:

> 기능 작업을 할 때마다 반복해서 수정되는 파일은 무엇인가?

---

# 원칙 4. 약속과 규칙을 코드로 확인할 수 있게 한다

사람에게는 "우리 프로젝트에서는 이렇게 해요"라는 말이 통할 수 있다.

Agent가 많아질수록 이 방식은 불안정하다.

중요한 약속은 가능한 한:

- type
- schema
- interface
- compiler
- lint
- architecture test
- compatibility test

로 확인할 수 있게 한다.

문서는 이유를 설명한다.

도구는 위반을 잡는다.

이 원칙이 해결하려는 문제:

- Agent마다 규칙을 다르게 해석함
- 서로 다른 가정으로 코드를 만듦
- 테스트만 통과하는 편법
- 문서와 코드가 달라짐

독자에게 던질 질문:

> 이 규칙을 어기면 사람이 리뷰하기 전에 기계가 알려주는가?

---

# 원칙 5. Agent가 수정한 결과를 바로 확인할 수 있게 한다

코드를 고친 다음 사람이 직접 확인해줘야 한다면 Agent는 반쪽짜리 자동화다.

Agent가 자기 결과를 스스로 확인할 수 있어야 한다.

그러려면 검증이:

- 빠르고
- 반복 가능하고
- 믿을 수 있고
- 무엇이 잘못됐는지 알려줘야 한다.

전체 테스트 하나만 있는 것보다 수정 영역 가까이에 빠른 검증 방법이 있어야 한다.

UI도 정상 화면뿐 아니라 오류, 빈 화면, 긴 글자 같은 상태를 바로 만들 수 있어야 한다.

이 원칙이 해결하려는 문제:

- 테스트가 너무 느림
- flaky test 때문에 정상 코드를 다시 고침
- UI 버그를 재현하지 못함
- 작업 완료를 너무 빨리 판단함

독자에게 던질 질문:

> Agent가 사람 도움 없이 "이 수정은 맞다"고 확인할 수 있는가?

---

# 원칙 6. 문제가 생기면 어디부터 볼지 바로 알 수 있게 한다

문제가 났을 때 Agent가 다시 저장소 탐색부터 시작하면 비용이 크다.

오류 메시지, 로그, 테스트 결과가 다음 행동을 알려줘야 한다.

예를 들어:

- 실패한 작업
- 깨진 규칙
- 관련 기능
- 관련 테스트
- 상세 로그 위치

정도가 연결돼 있으면 훨씬 빠르다.

이 원칙이 해결하려는 문제:

- generic error
- 거대한 로그
- 잘못된 파일을 계속 탐색
- debugging 중 수정 범위가 커짐

독자에게 던질 질문:

> 이 오류 하나만 보고 다음에 어디를 봐야 할지 알 수 있는가?

---

# 원칙 7. Agent에게 필요한 정보와 권한만 준다

많이 알려주면 더 잘할 것 같지만 꼭 그렇지는 않다.

관계없는 설명을 잔뜩 넣으면 오히려 중요한 정보가 묻힐 수 있다.

권한도 마찬가지다.

Agent가 알아서 필요한 권한만 안전하게 고를 것이라고 가정하지 않는다.

따라서:

- root 설명은 짧게
- 기능별 설명은 가까이에
- workspace는 작업별로 분리
- secrets와 production 권한은 분리
- 필요한 repository와 network만 허용

하는 방향이 좋다.

이 원칙이 해결하려는 문제:

- 불필요한 context
- 시키지 않은 수정
- 사고가 났을 때 큰 피해
- 작업 간 filesystem 오염

독자에게 던질 질문:

> 이 Agent에게 지금 작업과 관계없는 정보나 권한을 얼마나 주고 있는가?

---

# 원칙 8. 다음 Agent가 더 쉽게 일할 수 있게 끝낸다

현재 작업만 통과시키는 것은 충분하지 않다.

오늘 Agent가 남긴 코드가 내일 다른 Agent가 읽을 입력이 된다.

나쁜 예외와 중복을 계속 남기면 다음 Agent도 그 패턴을 따라간다.

따라서 완료에는 다음도 포함된다.

- 필요 없는 코드 제거
- 기존 규칙 유지
- 구조 위반 없음
- 테스트와 작업 상태 기록
- 다음 사람이 이어받을 수 있는 상태
- 반복되는 나쁜 패턴 정리

이 원칙이 해결하려는 문제:

- AI가 만든 작은 기술 부채 누적
- 다음 Agent의 작업 난이도 증가
- session이 끊기면 처음부터 다시 시작
- 기존 나쁜 코드 복제

독자에게 던질 질문:

> 이 작업이 끝난 뒤 다음 Agent의 일이 더 쉬워졌는가, 더 어려워졌는가?

---

# 이 8개가 기존 Clean Code와 다른 점

기존 Clean Code의 질문을 버리지는 않는다.

여전히 좋은 이름, 단순한 함수, 책임 분리, 테스트는 중요하다.

다만 질문의 범위를 넓힌다.

기존 질문:

> 이 코드는 읽기 좋은가?

Agentic 질문:

> 고칠 곳을 찾기 쉬운가?

기존 질문:

> 이 클래스의 책임이 분명한가?

Agentic 질문:

> 이 작업이 이 영역 안에서 끝나는가?

기존 질문:

> 테스트가 있는가?

Agentic 질문:

> Agent가 직접 빠르게 실행하고 결과를 믿을 수 있는가?

기존 질문:

> 오류 처리가 되어 있는가?

Agentic 질문:

> 오류를 보고 원인 코드까지 빨리 갈 수 있는가?

기존 질문:

> 문서가 있는가?

Agentic 질문:

> 필요한 정보만 필요한 순간에 찾을 수 있는가?

기존 질문:

> 리팩토링이 끝났는가?

Agentic 질문:

> 이 변경이 다음 Agent의 작업을 쉽게 만들었는가?

---

# 현재 단계의 정의

지금까지의 연구를 가장 쉬운 말로 줄이면 이렇다.

> **Agentic Clean Code는 Agent가 헤매지 않고, 필요한 곳만 고치고, 다른 Agent와 덜 부딪히고, 자기 결과를 직접 확인하고, 다음 Agent에게 더 나은 코드를 남길 수 있게 만드는 코드다.**

여기서 중요한 단어는 "Agent"보다 오히려 **헤매지 않는다, 덜 부딪힌다, 직접 확인한다, 다음 작업을 쉽게 만든다** 쪽이다.

그래서 이 원칙들은 AI 모델이 더 좋아져도 상당 부분 남을 가능성이 있다.

모델이 아무리 좋아져도:

- 불필요하게 강하게 결합된 코드는 강하게 결합돼 있고
- flaky test는 flaky하며
- 숨은 규칙은 숨은 규칙이고
- 동시에 같은 파일을 수정하면 충돌할 수 있기 때문이다.

# 다음 검증

이 8개를 바로 책의 최종 원칙으로 확정하지 않는다.

다음 단계에서는 각각에 대해 반론을 붙인다.

예:

- 모델이 충분히 좋아지면 "찾기 쉽게" 만들 필요가 줄어들지 않는가?
- 중앙 registry가 오히려 전체 구조를 이해하기 쉽게 만들 수도 있지 않은가?
- local test를 많이 만들면 유지보수 비용이 더 커지지 않는가?
- 규칙을 너무 많이 자동화하면 코드가 경직되지 않는가?
- Agent에 최적화하다 사람이 읽기 어려워지면 어떻게 할 것인가?

이 반론을 버티는 원칙만 책의 최종 원칙으로 남긴다.
