# Agentic Clean Code 원칙을 일부러 반박해보기

작성일: 2026-10-03  
상태: 리서치 v0.1

앞에서 8개의 원칙 후보를 만들었다.

이번에는 그 원칙을 지키는 방법이 아니라, **왜 그 원칙이 틀릴 수 있는지**부터 본다.

새로운 개발 방법론을 만들 때 가장 위험한 순간은 좋은 사례 몇 개를 보고 모든 프로젝트에 적용되는 규칙으로 바꾸는 순간이다.

Agentic Clean Code도 그렇게 되면 안 된다.

---

# 1. "고칠 곳을 찾기 쉽게 만든다"는 너무 당연한 말 아닌가

맞다.

이것만 놓고 보면 기존의 좋은 모듈화, 좋은 이름, 좋은 폴더 구조와 크게 다르지 않다.

또 모델이 계속 좋아지고 있다. 2026년에는 Coding Agent가 파일 시스템과 검색 도구를 사용해 매우 큰 자료를 처리하는 방식이 긴 문맥을 직접 넣는 것보다 좋은 결과를 보였다는 연구도 나왔다.

그렇다면 굳이 Agent를 위해 코드를 가까이 모아야 할까?

## 반론에 대한 현재 판단

**"Agent는 작은 코드만 읽을 수 있다"를 원칙의 근거로 삼으면 안 된다.**

모델의 문맥 길이는 계속 늘고, 검색과 요약 기술도 좋아질 것이다.

하지만 다른 연구에서는 버그 수정 과정에서 성공한 Agent가 실제로 사용한 문맥은 비교적 짧은 경우가 많았고, 문맥이 길어질수록 성공률이 떨어지는 현상도 관찰됐다.

중요한 것은 모델의 최대 문맥 크기가 아니다.

> 필요한 코드를 얼마나 적은 시행착오로 찾을 수 있는가.

따라서 원칙을 이렇게 고친다.

기존:

> 코드를 작게 나눠 Agent가 적게 읽게 한다.

수정:

> **코드 크기와 상관없이, 작업에 필요한 코드로 가는 길을 분명하게 만든다.**

큰 파일 하나가 오히려 이해하기 쉬운 경우도 있다.

작은 파일 50개에 로직을 흩어놓으면 더 나쁠 수 있다.

---

# 2. "한 작업은 한 영역에서 끝나게 한다"를 과하게 적용하면 어떻게 될까

이 원칙을 강하게 적용하면 모든 기능을 독립 모듈로 만들고 싶어진다.

조금 더 나가면 microservice가 많아질 수 있다.

그러면 새로운 문제가 생긴다.

- 네트워크 호출
- 장애 처리
- 배포 단위 증가
- 로그 추적 복잡도 증가
- 데이터 일관성 문제
- 개발 환경 복잡도 증가

Martin Fowler가 오래전부터 지적한 것처럼 강한 경계에는 비용이 있다. Microservice는 모듈 경계를 강하게 만들지만 분산 시스템의 비용을 함께 가져온다.

2025~2026년의 modular monolith 연구에서도 잘 나눈 하나의 애플리케이션이 운영 복잡도를 줄이는 실용적인 선택이 될 수 있다는 결과가 계속 나온다.

## 현재 판단

Agent를 많이 쓴다고 서비스를 잘게 나누는 것은 잘못된 결론이다.

중요한 것은 **배포 단위가 아니라 변경 단위**다.

다음 두 문장은 다르다.

> 모든 기능을 따로 배포한다.

> 서로 다른 이유로 바뀌는 기능의 내부 사정을 분리한다.

Agentic Clean Code가 원하는 것은 두 번째다.

따라서:

> **함께 바뀌어야 하는 코드를 억지로 떼지 않고, 따로 바뀌는 코드는 서로의 내부 사정을 몰라도 되게 만든다.**

가 더 정확하다.

---

# 3. "모두가 건드리는 중앙 파일을 없앤다"도 항상 맞을까

아니다.

중앙에 모아두는 것이 좋은 정보가 분명히 있다.

예를 들어:

- 시스템 전체 기능 목록
- 공개 API 목록
- 권한 정책의 기준
- 데이터 형식의 공식 정의
- 보안 정책
- 환경별 설정 기준

이런 정보까지 각 기능에 흩어놓으면 전체를 확인하기 어려워진다.

중요한 차이는 **한 곳에서 읽는 것**과 **모든 작업이 그 파일을 수정해야 하는 것**이다.

하나의 파일이 전체 구조를 보여주는 읽기 전용 색인이라면 도움이 될 수 있다.

문제는 기능을 하나 추가할 때마다 수십 Agent가 같은 파일을 직접 편집해야 하는 구조다.

## 현재 판단

원칙을 다음처럼 고친다.

> **중앙화를 없애는 것이 아니라, 중앙의 기준과 중앙의 수정 병목을 구분한다.**

예를 들어 각 모듈이 자기 정보를 가지고 있고 build 과정에서 전체 목록을 자동 생성할 수 있다면:

- 정보의 기준은 각 모듈에 있고
- 전체를 보는 화면도 있으며
- Agent들이 같은 파일을 직접 수정할 필요는 없다.

이 방식이 더 좋은 경우가 많다.

---

# 4. "규칙은 코드로 검사한다"를 너무 많이 하면 코드가 경직되지 않을까

그렇다.

자동 검사할 수 있다고 모든 것을 검사하면 안 된다.

예를 들어:

- 폴더는 반드시 3단계여야 한다.
- 클래스 이름은 반드시 특정 접미사를 가져야 한다.
- 모듈은 정확히 N개 이하여야 한다.
- 모든 함수는 N줄 이하여야 한다.

같은 것을 architecture rule로 만들면 정상적인 리팩토링까지 막을 수 있다.

Architecture Fitness Function도 구조를 검사할 수 있을 뿐, 그 구조가 좋은 설계인지까지 판단하지는 못한다.

자동 규칙은 최소 기준이다.

설계 판단을 대신할 수 없다.

## 현재 판단

기계가 검사해야 하는 것은 **취향이 아니라 오래 유지할 약속**이다.

좋은 후보:

- domain이 infrastructure를 직접 참조하지 않는다.
- 공개하지 않은 내부 API를 다른 모듈이 쓰지 않는다.
- 순환 의존성이 없다.
- 특정 보안 규칙을 우회하지 않는다.

나쁜 후보:

- 현재 폴더 모양을 영원히 고정
- 개인적인 코드 스타일
- 아직 안정되지 않은 설계 선택

따라서:

> **자주 바뀌지 않는 중요한 약속만 자동으로 막는다.**

---

# 5. "수정한 뒤 바로 확인할 수 있어야 한다"면 작은 테스트만 있으면 될까

아니다.

작은 테스트만 빠르게 돌리는 구조에도 문제가 있다.

각 기능은 모두 성공하지만 실제로 합치면 실패할 수 있다.

mock이 실제 시스템과 달라질 수도 있다.

특히 여러 Agent가 동시에 작업하면 각자 local test는 통과했는데 통합 뒤 깨지는 상황이 생길 수 있다.

## 현재 판단

빠른 테스트와 전체 검증 중 하나를 고르는 문제가 아니다.

순서가 중요하다.

1. 수정한 영역에서 몇 초 안에 확인
2. 연결된 영역 확인
3. 합쳐진 변경 확인
4. 필요한 경우 전체 검사

즉:

> **가까운 곳에서 빠르게 확인하고, 멀리 퍼지는 문제는 단계적으로 확인한다.**

Agent에게 빠른 첫 피드백을 주되 local test만 믿게 해서는 안 된다.

---

# 6. "오류가 다음에 볼 곳을 알려준다"면 로그를 많이 남기면 될까

아니다.

로그가 많으면 오히려 찾기 어려워질 수 있다.

또 로그에 사용자 정보, token, 개인정보, 내부 데이터가 섞이면 보안 문제가 생긴다.

Agent가 읽기 좋게 만들겠다고 모든 내부 상태를 출력하는 것도 잘못이다.

## 현재 판단

좋은 오류의 핵심은 정보의 양이 아니라 **방향**이다.

첫 실패 정보는 짧게 남기고:

- 무슨 작업이 실패했는지
- 어떤 종류의 문제인지
- 어디를 더 보면 되는지
- 상세 정보는 어디에 있는지

정도만 알려준다.

민감한 값은 남기지 않는다.

즉:

> **로그를 많이 주는 것이 아니라, 다음 탐색을 줄이는 정보를 준다.**

---

# 7. "필요한 정보만 준다"를 너무 줄이면 오히려 Agent가 실수하지 않을까

맞다.

AGENTS.md 연구가 "문서는 필요 없다"고 말하는 것은 아니다.

연구에서도 Agent는 주어진 지침을 잘 따랐다.

문제는 일반적인 저장소 설명과 불필요한 요구사항까지 많이 넣었을 때 작업 성공률이 좋아지지 않고 비용이 늘었다는 점이다.

프로젝트만의 특별한 규칙은 여전히 알려줘야 한다.

예:

- 이 저장소는 특정 code generator를 반드시 사용
- migration 파일 직접 수정 금지
- 특정 테스트 명령 사용
- 보안상 접근 금지 영역

이런 정보는 모델이 추측할 수 없다.

## 현재 판단

최소한으로 줄이는 것이 목표가 아니다.

> **이 작업에 필요한 특별한 사실을 빠뜨리지 않고, 이미 코드와 도구가 알려주는 일반적인 내용은 반복하지 않는다.**

이를 "최소 문서"보다 **필요한 문서**라고 표현하는 편이 독자에게 낫다.

---

# 8. "다음 Agent가 쉽게 일하게 끝낸다"가 작업 범위를 키우지 않을까

그럴 수 있다.

이 원칙을 잘못 적용하면 Agent가:

> 다음 사람을 위해 이것도 정리했습니다.

라고 하며 요청하지 않은 리팩토링을 잔뜩 할 수 있다.

앞에서 조사한 "시키지 않은 것까지 건드린다" 문제와 정면으로 충돌한다.

## 현재 판단

다음 Agent를 위해 좋게 만든다는 뜻은 주변 코드를 마음대로 정리한다는 뜻이 아니다.

더 정확한 원칙은:

> **내가 건드린 곳을 더 나쁜 상태로 남기지 않고, 추가 정리가 필요하면 별도 작업으로 남긴다.**

즉 작업 범위를 지키는 것이 먼저다.

큰 cleanup이 필요하면 현재 feature diff에 끼워 넣지 않는다.

---

# 9. 가장 중요한 반론: Agent에게 맞추다가 사람이 읽기 어려워지면?

이 질문은 책 전체에서 계속 확인해야 한다.

Agent 때문에:

- 파일을 지나치게 많이 나누고
- 사람에게는 필요 없는 metadata를 넣고
- 로그를 기계 중심으로 만들고
- 복잡한 자동 규칙을 추가하고
- 사람이 이해하기 어려운 generated structure를 만들 수 있다.

그렇게 되면 좋은 방향이라고 보기 어렵다.

현재 연구에서는 사람에게 읽기 좋은 코드와 Agent가 안전하게 다룰 수 있는 코드가 완전히 반대라는 근거는 약하다.

오히려 명확한 이름, 분명한 책임, 예측 가능한 구조, 테스트 가능성은 둘 모두에게 도움이 되는 경우가 많다.

따라서 책 전체에 다음 상위 원칙을 둔다.

> **Agent에게 좋다는 이유만으로 사람에게 나쁜 코드를 만들지 않는다.**

Agentic Clean Code는 Human Clean Code를 대체하는 것이 아니라 그 위에 필요한 조건을 추가해야 한다.

---

# 10. 또 하나의 반론: 모델이 좋아지면 이 책이 필요 없어지지 않을까

일부 원칙은 약해질 것이다.

예:

- 단순한 검색 문제
- 긴 코드 이해
- 문서 요약
- 특정 도구 사용법

은 모델 발전으로 줄어들 가능성이 높다.

그래서 원칙을 모델의 현재 약점에 맞추면 안 된다.

반면 다음 문제는 모델 성능과 별개로 남을 가능성이 높다.

- 두 작업이 실제로 같은 파일을 수정함
- 서로 다른 코드가 같은 숨은 규칙에 의존함
- 테스트가 무작위로 실패함
- 환경마다 결과가 다름
- 권한이 필요 이상으로 큼
- 중요한 규칙이 실제 코드와 다름

이것들은 더 똑똑한 모델만으로 없어지는 문제가 아니다.

따라서 최종 원칙은 **모델의 지능 부족이 아니라 소프트웨어 구조 자체의 문제**에 집중해야 한다.

---

# 11. 이번 반론 검토로 바뀐 생각

### 버리는 표현

- 무조건 작게 쪼갠다.
- 중앙 파일을 없앤다.
- 문서를 최소화한다.
- 모든 규칙을 자동화한다.
- local test가 빠르면 된다.
- Agent를 위해 코드를 최적화한다.

### 남기는 표현

- 필요한 코드로 가는 길을 분명하게 한다.
- 실제 변경 이유에 맞게 경계를 나눈다.
- 여러 작업이 동시에 수정해야 하는 지점을 줄인다.
- 오래 유지할 중요한 약속은 자동으로 확인한다.
- 가까운 곳부터 빠르게, 마지막에는 통합해서 확인한다.
- 특별한 정보는 주되 불필요한 설명은 줄인다.
- Agent와 사람 모두 이해할 수 있는 구조를 우선한다.
